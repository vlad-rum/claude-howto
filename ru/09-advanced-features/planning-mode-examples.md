# Примеры режима планирования

Реальные примеры, которые показывают, как эффективно пользоваться режимом планирования в Claude Code.

## Пример 1: создание REST API

### Без режима планирования

```
Пользователь: Собери REST API для блога

Claude: Я создам API...
[Сразу начинает писать код и может упустить требования]
```

### С режимом планирования

```
Пользователь: /plan Собери REST API для блога

Claude: Составлю полный план API блога.

## План реализации REST API блога

### Фаза 1: подготовка проекта (15 мин)
1. Инициализировать проект Node.js с Express
2. Настроить конфигурацию TypeScript
3. Установить зависимости (express, pg, jwt, joi)
4. Настроить переменные окружения
5. Задать структуру проекта

### Фаза 2: слой базы данных (30 мин)
6. Спроектировать схему базы данных
   - таблица users (id, email, password_hash, created_at)
   - таблица posts (id, user_id, title, content, published, created_at, updated_at)
   - таблица comments (id, post_id, user_id, content, created_at)
7. Создать файлы миграций
8. Настроить пул соединений с базой данных
9. Реализовать модели базы данных

### Фаза 3: аутентификация (45 мин)
10. Реализовать эндпоинт регистрации пользователя
11. Реализовать эндпоинт входа с JWT
12. Создать промежуточное ПО аутентификации
13. Добавить хеширование паролей через bcrypt
14. Реализовать логику обновления токена

### Фаза 4: API постов (40 мин)
15. GET /api/posts — список всех опубликованных постов (с пагинацией)
16. GET /api/posts/:id — получить один пост
17. POST /api/posts — создать пост (нужна аутентификация)
18. PUT /api/posts/:id — обновить пост (нужна аутентификация, проверка владельца)
19. DELETE /api/posts/:id — удалить пост (нужна аутентификация, проверка владельца)
20. GET /api/users/:id/posts — получить посты пользователя

### Фаза 5: API комментариев (30 мин)
21. GET /api/posts/:id/comments — получить комментарии поста
22. POST /api/posts/:id/comments — добавить комментарий (нужна аутентификация)
23. DELETE /api/comments/:id — удалить комментарий (нужна аутентификация, проверка владельца)

### Фаза 6: проверка и обработка ошибок (30 мин)
24. Добавить проверку запросов через Joi
25. Реализовать глобальный обработчик ошибок
26. Добавить очистку входных данных
27. Реализовать лимит запросов

### Фаза 7: тестирование (60 мин)
28. Написать модульные тесты моделей
29. Написать интеграционные тесты эндпоинтов аутентификации
30. Написать интеграционные тесты эндпоинтов постов
31. Написать интеграционные тесты эндпоинтов комментариев
32. Достичь покрытия кода 80%+

### Фаза 8: документация и деплой (30 мин)
33. Сгенерировать документацию API через Swagger
34. Создать README с инструкцией по настройке
35. Добавить конфигурацию Docker
36. Настроить пайплайн CI/CD

**Оценка времени**: 4,5 часа
**Файлов создать**: ~25
**Ключевые технологии**: Express, PostgreSQL, JWT, TypeScript

**Сводка эндпоинтов API**:
- Аутентификация: 2 эндпоинта
- Посты: 6 эндпоинтов
- Комментарии: 3 эндпоинта
- Всего: 11 эндпоинтов

Продолжать? (да/нет/изменить)

Пользователь: да

Claude: Начинаю фазу 1: подготовка проекта...
[Реализует каждую фазу по порядку]
```

## Пример 2: миграция базы данных

### С режимом планирования

```
Пользователь: /plan Перейди с MongoDB на PostgreSQL

Claude: Это сложная миграция. Составлю подробный план.

## План миграции с MongoDB на PostgreSQL

### Фаза 1: анализ и подготовка (день 1)
1. Проанализировать текущую схему MongoDB
2. Выявить связи данных и ограничения
3. Зафиксировать текущий объём данных и темп роста
4. Спроектировать эквивалентную схему PostgreSQL
5. Спланировать соответствие типов данных
6. Выявить возможные трудности миграции

### Фаза 2: настройка PostgreSQL (день 1)
7. Поднять базу данных PostgreSQL
8. Создать схему с таблицами, индексами и ограничениями
9. Настроить пул соединений
10. Настроить стратегию резервного копирования

### Фаза 3: реализация двойной записи (дни 2–3)
11. Создать слой абстракции базы данных
12. Реализовать двойную запись в обе базы
13. Добавить проверки согласованности данных
14. Выкатить двойную запись на стейджинг
15. Следить за проблемами

### Фаза 4: миграция данных (день 4)
16. Создать скрипты экспорта данных из MongoDB
17. Создать скрипты импорта данных в PostgreSQL
18. Реализовать логику преобразования данных
19. Прогнать первую миграцию на копии продакшен-данных
20. Проверить целостность перенесённых данных

### Фаза 5: постепенное переключение (дни 5–7)
21. Включить двойную запись в продакшене
22. Переносить исторические данные пакетами
23. Непрерывно проверять согласованность данных
24. Наблюдать за обеими базами
25. Исправить любые рассинхронизации данных

### Фаза 6: PostgreSQL как основная база (день 8)
26. Переключить операции чтения на PostgreSQL
27. Наблюдать за производительностью запросов
28. Оптимизировать медленные запросы
29. Продолжить двойную запись для безопасности

### Фаза 7: вывод MongoDB из эксплуатации (дни 9–10)
30. Прекратить запись в MongoDB
31. Оставить MongoDB как резерв на 2 недели
32. Убрать зависимости MongoDB из кода
33. Заархивировать данные MongoDB
34. Вывести экземпляр MongoDB из эксплуатации

**Оценка времени**: 10 дней
**Уровень риска**: высокий
**Стратегия отката**: держать MongoDB запущенной с двойной записью
**Критерии успеха**:
- Нулевая потеря данных
- Регресс производительности <5%
- Все тесты проходят

**Ключевые риски**:
1. Несогласованность данных во время миграции
2. Падение производительности запросов
3. Простой приложения
4. Потеря данных

**Снижение рисков**:
- Шаблон двойной записи для безопасности
- Постепенное переключение
- Непрерывное наблюдение
- Быстрая возможность отката

Продолжать по этому плану? (да/нет/изменить)

Пользователь: изменить — добавим план отката для каждой фазы

Claude: Обновлённый план с процедурами отката для каждой фазы...
```

## Пример 3: рефакторинг фронтенда

```
Пользователь: /plan Отрефакторь наше React-приложение: классовые компоненты заменить на хуки

Claude: Составлю системный план рефакторинга.

## План миграции с классов React на хуки

### Фаза 1: подготовка и анализ (2 часа)
1. Провести аудит всех классовых компонентов (найти все файлы .jsx/.tsx)
2. Разбить по сложности:
   - простые (только состояние): ~15 компонентов
   - средние (методы жизненного цикла): ~23 компонента
   - сложные (несколько методов жизненного цикла, рефы): ~8 компонентов
3. Выявить сторонние библиотеки, которые нужно обновить
4. Построить граф зависимостей компонентов
5. Спланировать порядок миграции (сначала листовые узлы)

### Фаза 2: настройка и инструменты (1 час)
6. Обновить React до v18+
7. Настроить правила ESLint для хуков
8. Создать шаблоны преобразования
9. Настроить автоматические тесты
10. Создать контрольную точку перед стартом

### Фаза 3: миграция простых компонентов (4 часа)
11. Преобразовать простые компоненты с состоянием (15 компонентов)
12. Заменить this.state на useState
13. Заменить this.setState на сеттеры состояния
14. Протестировать каждый компонент после преобразования
15. Обновить тесты

### Фаза 4: миграция средних компонентов (8 часов)
16. Преобразовать компоненты с методами жизненного цикла (23 компонента)
17. Заменить componentDidMount на useEffect
18. Заменить componentDidUpdate на useEffect
19. Заменить componentWillUnmount на очистку useEffect
20. Тщательно протестировать

### Фаза 5: миграция сложных компонентов (12 часов)
21. Преобразовать сложные компоненты (8 компонентов)
22. Заменить рефы на useRef
23. Вынести общие хуки для разделяемой логики
24. Обработать граничные случаи (несколько useEffect)
25. Обширное тестирование

### Фаза 6: выделение общей логики (6 часов)
26. Найти дублирующуюся логику между компонентами
27. Создать свои хуки:
    - useAuth
    - useFetch
    - useLocalStorage
    - useDebounce
28. Отрефакторить компоненты на свои хуки
29. Протестировать свои хуки отдельно

### Фаза 7: оптимизация производительности (4 часа)
30. Добавить React.memo там, где нужно
31. Оптимизировать через useCallback
32. Оптимизировать через useMemo
33. Снять профиль и исправить регрессы производительности

### Фаза 8: очистка и документация (2 часа)
34. Удалить неиспользуемые утилиты классовых компонентов
35. Обновить документацию
36. Обновить правила написания кода
37. Создать руководство по миграции для команды

**Оценка времени**: 5 дней (39 часов)
**Файлов изменить**: 46 компонентов
**Уровень риска**: средний

**Порядок миграции**:
1. Листовые компоненты (без зависимостей)
2. Компоненты среднего уровня
3. Контейнерные компоненты верхнего уровня
4. App.jsx (в конце)

**Стратегия тестирования**:
- Модульные тесты каждого компонента
- Интеграционные тесты пользовательских сценариев
- Тесты визуальной регрессии
- Замеры производительности

**Метрики успеха**:
- Все тесты проходят
- Нет визуальных регрессий
- Производительность сохранена или выросла
- Размер бандла существенно не вырос

Продолжать? (да/нет/изменить)
```

## Главные выводы

### Польза режима планирования

1. **Ясность**: ясная дорожная карта до старта
2. **Оценка**: оценки времени и усилий
3. **Оценка рисков**: возможные проблемы видны заранее
4. **Приоритизация**: логичный порядок задач
5. **Одобрение**: план проверяют и одобряют до выполнения
6. **Правки**: план подстраивается под обратную связь

### Когда использовать режим планирования

✅ **Всегда используйте для**:
- Проектов на несколько дней
- Совместной работы команды
- Критичных изменений системы
- Изучения новых концепций
- Сложного рефакторинга

❌ **Не используйте для**:
- Исправления багов
- Мелких правок
- Простых вопросов
- Быстрых экспериментов
