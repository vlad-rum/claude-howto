## Обзор

Продвинутые функции Claude Code расширяют базовые возможности планированием, рассуждением, автоматизацией и механизмами контроля. С ними можно строить сложные рабочие процессы для комплексных задач разработки, код-ревью, автоматизации и управления несколькими сессиями.

**Ключевые продвинутые функции:**
- **Режим планирования**: подробный план реализации до написания кода
- **Расширенное мышление**: глубокое рассуждение для сложных задач
- **Режим Auto**: фоновый классификатор безопасности проверяет каждое действие перед выполнением
- **Фоновые задачи**: долгие операции без блокировки разговора
- **Режимы разрешений**: контроль того, что может делать Claude (`manual` — раньше `default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`)
- **Режим print**: неинтерактивный запуск Claude Code для автоматизации и CI/CD (`claude -p`)
- **Управление сессиями**: несколько рабочих сессий
- **Интерактивные функции**: сочетания клавиш, многострочный ввод и история команд
- **Голосовой ввод**: голосовой ввод в режиме «нажми и говори» с распознаванием речи (STT) на 20 языках
- **Каналы**: MCP-серверы отправляют сообщения в запущенные сессии (Research Preview)
- **Remote Control**: управление Claude Code из Claude.ai или приложения Claude
- **Веб-сессии**: Claude Code в браузере на claude.ai/code
- **Приложение Desktop**: отдельное приложение для визуального просмотра diff и нескольких сессий
- **Список задач**: постоянное отслеживание задач между сжатиями контекста
- **Подсказки промптов**: умные подсказки команд по контексту
- **Git Worktrees**: изолированные ветки worktree для параллельной работы
- **Песочница**: изоляция файловой системы и сети на уровне ОС
- **Управляемые настройки**: корпоративный деплой через plist, Registry или управляемые файлы
- **Конфигурация**: настройка поведения через файлы конфигурации JSON

## Режим планирования

Режим планирования позволяет Claude обдумать сложную задачу до реализации и составить подробный план, который вы проверяете и одобряете.

### Что такое режим планирования?

Режим планирования состоит из двух фаз:
1. **Фаза планирования**: Claude анализирует задачу и составляет подробный план реализации
2. **Фаза реализации**: после одобрения Claude выполняет план

### Когда использовать режим планирования

✅ Используйте режим планирования для:
- Сложного рефакторинга многих файлов
- Реализации новых функций
- Архитектурных изменений
- Миграций базы данных
- Крупных переработок API

❌ Не используйте режим планирования для:
- Простых исправлений ошибок
- Изменений форматирования
- Правок в одном файле
- Быстрых вопросов

### Активация режима планирования

**Слэш-команда**:
```bash
/plan Реализуй систему аутентификации пользователей
```

**Флаг CLI**:
```bash
claude --permission-mode plan
```

**Режим по умолчанию**:
```json
{
  "permissions": {
    "defaultMode": "plan"
  }
}
```

**Сочетание клавиш**:
- `Shift + Tab` — переключение режимов разрешений (включая plan)
- `Alt + M` — переключение режимов разрешений (только Windows, если среда выполнения не включает режим ввода VT)

### Преимущества режима планирования

- **Структурированный подход к реализации**: подробная разбивка шагов
- **Проверка и одобрение**: одобрите или поправьте план до выполнения
- **Выявление рисков**: возможные проблемы видны до реализации
- **Понятные фазы**: упорядоченные фазы реализации и контрольные точки

### Пример: реализация функции

```
Пользователь: /plan Добавь систему уведомлений в реальном времени

Claude: Составлю план реализации уведомлений в реальном времени.

## План реализации

### Фаза 1: настройка инфраструктуры
1. Установить библиотеки WebSocket (socket.io)
2. Поднять сервер WebSocket
3. Настроить управление соединениями

### Фаза 2: реализация бэкенда

5. Реализовать очередь уведомлений
6. Добавить схему базы данных для уведомлений
7. Создать конечные точки API

### Фаза 3: интеграция фронтенда
8. Настроить клиент WebSocket
9. Создать UI-компоненты уведомлений
10. Реализовать управление состоянием уведомлений
11. Добавить разрешения на уведомления

### Фаза 4: тестирование и деплой
12. Написать модульные тесты
13. Написать интеграционные тесты
14. Обновить документацию
15. Задеплоить на staging

Оценка времени: 3–4 часа
Файлов к изменению: 12

Продолжать? (да/нет/изменить план)

Пользователь: да

Claude: [Начинает реализацию по плану]
```

### Изменения плана

```
Пользователь: Измени план — очередь пока пропусти, добавим её позже

Claude: Обновлённый план:
[Показывает изменённый план без очереди]

Пользователь: Выглядит хорошо, продолжай

Claude: [Выполняет изменённый план]
```

### Настройка режима планирования

Режим планирования включается флагом CLI или слэш-командой:

```bash
# Активация режима планирования через CLI
claude --permission-mode plan

# Или слэш-команда /plan внутри REPL
/plan Реализуй систему аутентификации пользователей
```

**Псевдоним модели для планирования**: используйте псевдоним `opusplan`, чтобы планировать на Opus, а выполнять на Sonnet:

```bash
claude --model opusplan "спроектируй и реализуй новый API"
```

**Внешняя правка плана**: нажмите `Ctrl+G`, чтобы открыть текущий план во внешнем редакторе и подробно его изменить.

> **Обновление v2.1.112**: файлы планов теперь называются по промпту, который их породил (а не случайными словами), поэтому их проще просматривать и переиспользовать.

> **Обновление v2.1.136 — блокировка записи в режиме планирования безусловна**: режим планирования теперь блокирует любую запись в файлы, в том числе если в `permissions.allow` есть подходящее правило `Edit(...)`. Раньше слишком широкое правило `Edit(...)` могло пропускать запись в режиме планирования; этот обход закрыт. Если рабочий процесс зависел от старого поведения, выйдите из режима планирования (`Shift+Tab`) перед правкой.

## Расширенное мышление

Расширенное мышление позволяет Claude дольше рассуждать над сложной задачей, прежде чем предложить решение.

### Что такое расширенное мышление?

Расширенное мышление — это намеренный пошаговый процесс рассуждения, в котором Claude:
- Разбивает сложные задачи
- Рассматривает несколько подходов
- Оценивает компромиссы
- Продумывает граничные случаи

### Активация расширенного мышления

**Сочетание клавиш**:
- `Option + T` (macOS) / `Alt + T` (Windows/Linux) — переключение расширенного мышления. На Opus 5.5 (модель по умолчанию с v2.1.280), Sonnet 5.5, Haiku 5.5 и моделях Fable мышление нельзя выключить — переключатель, `alwaysThinkingEnabled` и `MAX_THINKING_TOKENS=0` там не действуют.

**Автоматическое включение**:
- Включено по умолчанию для всех моделей (Opus 5, Opus 4.8, Opus 4.7, Sonnet 4.6, Haiku 4.5)
- Opus 5 / Opus 4.8: адаптивное рассуждение с уровнями усилия: `low` (○), `medium` (◐), `high` (●), `xhigh`, `max`. По умолчанию стоит `medium` на Opus 5.5 (модель по умолчанию с v2.1.280), Sonnet 5.5 и Haiku 5.5, `high` на Opus 5 (v2.1.219), Sonnet 5, Opus 4.8 (v2.1.154), Opus 4.6 и Sonnet 4.6, и `xhigh` на Opus 4.7. `xhigh` доступен на Opus 5.5, Sonnet 5.5, Haiku 5.5, Opus 5, Sonnet 5, Opus 4.8 и Opus 4.7 (на Opus 4.6 / Sonnet 4.6 он откатывается к `high`). `max` работает на Opus 5.5, Sonnet 5.5, Haiku 5.5, Opus 5, Sonnet 5, а также на Opus 4.8/4.7/4.6 и Sonnet 4.6 (только в рамках сессии). У Haiku 4.5 уровней усилия нет. У Opus 5, Opus 4.8 и Opus 4.7 нативное контекстное окно на 1 млн токенов (исправление контекста 1M вошло в v2.1.117 — до этого `/context` ошибочно считал Opus 4.7 относительно окна 200K и слишком рано запускал autocompact). С v2.1.129 `/context` показывает визуализацию только в интерфейсе; ASCII-схема больше не попадает в контекст разговора (экономия ~1,6 тыс. токенов на вызов), поэтому `/context` можно вызывать свободно.
- Подписчики Pro/Max на Opus 4.6 / Sonnet 4.6: уровень усилия по умолчанию повышен с `medium` до `high` в v2.1.117.
- Остальные модели: фиксированный бюджет до 31 999 токенов

**Способы настройки**:
- Переключатель: `Alt+T` / `Option+T` или через `/config`
- Просмотр рассуждения: `Ctrl+O` (подробный режим)
- Уровень усилия: команда `/effort` или флаг `--effort`

**Свой бюджет**:
```bash
export MAX_THINKING_TOKENS=1024
```

**Уровень усилия** (поддерживается на Opus 5.5, Sonnet 5.5, Haiku 5.5, Opus 5, Sonnet 5, Opus 4.8, Opus 4.7, Opus 4.6 и Sonnet 4.6 — не на Haiku 4.5):
```bash
export CLAUDE_CODE_EFFORT_LEVEL=high   # low (○), medium (◐), high (●), xhigh (Opus 5.5, Sonnet 5.5, Haiku 5.5, Opus 5, Sonnet 5, Opus 4.8/4.7) или max — по умолчанию high на Opus 5 и Opus 4.8
```

**Флаг CLI**:
```bash
claude --effort high "сложное архитектурное ревью"
```

**Слэш-команда**:
```
/effort high
```

> **Примечание.** Ключевое слово «ultrathink» в промптах включает режим глубокого рассуждения. Уровни усилия `low`, `medium`, `high` и `max` поддерживаются на Opus 5.5, Sonnet 5.5, Haiku 5.5, Opus 5, Sonnet 5, Opus 4.8, Opus 4.7, Opus 4.6 и Sonnet 4.6 (у Haiku 4.5 их нет). `xhigh` доступен на Opus 5.5, Sonnet 5.5, Haiku 5.5, Opus 5, Sonnet 5, Opus 4.8 и Opus 4.7. Усилие по умолчанию — `medium` на Opus 5.5, Sonnet 5.5 и Haiku 5.5, `high` на Opus 5, Sonnet 5, Opus 4.8 (а также Opus 4.6 / Sonnet 4.6) и `xhigh` на Opus 4.7. В отличие от Opus 4.8 и Opus 4.7, которые фиксируют усилие по умолчанию при первом запуске, у Opus 5 такой фиксации нет — ранее выбранный уровень сохраняется. У ползунка `/effort` также есть переключатель **Ultracode** (Tab или `/effort ultracode [on|off]`). Это **не** уровень усилия модели: Claude оркестрирует динамические Workflows на том уровне усилия, на котором идёт сессия. С v2.1.284 переключатель больше не принудительно ставит `xhigh` и остаётся включённым, когда вы меняете уровень; `--effort ultracode` и `effortLevel: "ultracode"` в Agent SDK по-прежнему ставят `xhigh`.

### Резервное переключение классификатора безопасности на Opus 5

Отдельно от [настройки `fallbackModel`](#запасные-модели-fallbackmodel) (она обрабатывает перегрузку и недоступность) Claude Code применяет **резервное переключение по категории**, когда классификатор безопасности помечает запрос. Нужен Claude Code v2.1.219 или новее.

- **Opus 5**: запросы, помеченные как кибербезопасность, выполняются заново на Opus 4.8. Запросы, помеченные как биология, заканчиваются отказом: у Opus 5 собственные классификаторы биологии, и запасной модели для них нет. Эти отказы приходят уже с первого помеченного запроса.
- Нагрузки в области наступательной безопасности или биологии — тестирование на проникновение, упражнения Capture the Flag (CTF) и кодовые базы, смежные с биологией, — часто вызывают переключение, нередко уже на первом запросе.

Почему это важно здесь: если вы запускаете [субагентов security-review](../04-subagents/README.md) или работу CTF/pentest на Opus 5, ждите тихих повторных запусков на Opus 4.8 (другой потолок усилия и другое контекстное окно) для промптов по кибербезопасности и прямых отказов для запросов, смежных с биологией. Если такое поведение мешает, явно зафиксируйте другую модель.

**Управление переключением** — настройка `switchModelsOnFlag` (v2.1.170+, по умолчанию `true`) решает, происходит ли запасной переход молча. Поставьте `false`, и Claude Code остановится, чтобы вы выбрали: переключить модель или отредактировать промпт. В `/config` это пункт **Switch models when a message is flagged**.

```json
{
  "switchModelsOnFlag": false
}
```

### Преимущества расширенного мышления

- **Глубокое рассуждение**: больше времени на обдумывание сложных задач
- **Более удачные архитектурные решения**: осознанный выбор после всесторонней оценки
- **Учёт граничных случаев**: проработка возможных проблем и сценариев
- **Тщательный анализ**: структурированный подход к сложным задачам

```
## Анализ контекста
- Размер команды: 5 разработчиков
- Ожидаемый трафик: сначала 10 тыс. пользователей в день
- Нужно масштабироваться до 100 тыс.+ пользователей
- Ограниченные ресурсы DevOps
- 6 месяцев до MVP

## Подход 1: микросервисы
Плюсы:
+ Независимое масштабирование
+ Гибкость технологий
+ Независимость команд
+ Изоляция сбоев

Минусы:
- Операционная сложность
- Сетевые накладные расходы
- Нужна распределённая трассировка
- Требуется экспертиза DevOps
- Медленнее старт разработки

## Подход 2: монолит
Плюсы:
+ Проще деплой
+ Быстрее старт разработки
+ Проще отладка
+ Ниже операционные расходы
+ Одна кодовая база

Минусы:
- Сложности масштабирования позже
- Деплой «всё или ничего»
- Привязка к технологиям
- Риск тесной связанности

## Факторы решения
1. Размер команды (5 разработчиков) → в пользу монолита
2. Ресурсы DevOps (ограничены) → в пользу монолита
3. Срок (6 месяцев) → в пользу монолита
4. Будущий масштаб (100 тыс. пользователей) → достижим монолитом и кэшированием
5. Бюджет сложности → ограничен

## Рекомендация
Начните с **модульного монолита**:
- Одна единица деплоя
- Чёткие границы модулей
- Чистые интерфейсы между модулями
- Готовность позже выделить микросервисы, если понадобится

Это даёт:
✓ Быстрый старт разработки
✓ Низкую операционную сложность
✓ Возможность позже выделить сервисы
✓ Понятную архитектуру

Путь миграции: когда вы дойдёте до 50 тыс.+ пользователей или отдельным модулям понадобится независимое масштабирование, выделите эти модули в микросервисы.
</extended_thinking>

**Рекомендация**: реализуйте модульный монолит с чёткими границами модулей.

Такой подход уравновешивает текущие ограничения (размер команды, срок, ресурсы DevOps) и будущие потребности в масштабировании. Отдельные модули можно перенести в микросервисы позже, когда появится явная бизнес-потребность.
```

### Настройка расширенного мышления

Расширенное мышление управляется переменными окружения, сочетаниями клавиш и флагами CLI:

```bash
# Задать бюджет токенов мышления
export MAX_THINKING_TOKENS=16000

# Задать уровень усилия (Opus 5.5, Sonnet 5.5, Haiku 5.5, Opus 5, Sonnet 5, Opus 4.8, Opus 4.7, Opus 4.6, Sonnet 4.6): low (○), medium (◐), high (●), xhigh (Opus 5.5, Sonnet 5.5, Haiku 5.5, Opus 5, Sonnet 5, Opus 4.8/4.7) или max — по умолчанию high на Opus 5 и Opus 4.8
```

> **Облегчённый системный промпт (v2.1.154).** Облегчённый системный промпт теперь **по умолчанию** для всех моделей, кроме Haiku 4.5, Sonnet 5, Opus 4.7 и более ранних моделей этих семейств (Haiku 5.5 и Sonnet 5.5 его тоже используют). Это снижает базовые накладные расходы по токенам на Opus 5 и Opus 4.8.

## Режим Auto

Режим Auto — это режим разрешений, в котором фоновый классификатор безопасности проверяет каждое действие перед выполнением. Claude работает автономно и при этом блокирует опасные операции. Режим доступен на всех планах, но нужна подходящая модель (Claude Opus 4.6 или новее, Sonnet 4.6 или новее, Haiku 5.5 либо модель Fable на Anthropic API и Claude Platform on AWS; Sonnet 5 или новее, Opus 4.7 или новее, Haiku 5.5 либо модель Fable на Bedrock, Vertex, Foundry и в сессиях шлюза приложений Claude со входом). На Team и Enterprise он включён по умолчанию — администраторы могут отключить его для организации в управляемых настройках.

### Требования

Режим Auto доступен, только если учётная запись удовлетворяет всем этим требованиям:

- **План**: все планы.
- **Организация**: на Team и Enterprise режим Auto доступен по умолчанию. Администраторы могут отключить его для организации, установив `permissions.disableAutoMode` в `"disable"` в управляемых настройках.
- **Модель**: на Anthropic API и Claude Platform on AWS — Claude Opus 4.6 или новее, Sonnet 4.6 или новее, Haiku 5.5 либо модель Fable. На Amazon Bedrock, Agent Platform от Google Cloud (Vertex AI), Microsoft Foundry и в сессиях шлюза приложений Claude со входом — только Claude Sonnet 5 или новее, Opus 4.7 или новее, Haiku 5.5 (v2.1.293+) и модели Fable. Более старые модели — Sonnet 4.5, Opus 4.5, Haiku 4.5 и модели claude-3 — не поддерживаются ни у одного провайдера.
- **Провайдер**: по умолчанию доступен на Anthropic API, Claude Platform on AWS, Amazon Bedrock, Agent Platform от Google Cloud (Vertex AI), Microsoft Foundry и в сессиях шлюза приложений Claude со входом. В v2.1.158–v2.1.206 режим Auto был выключен на всех этих платформах, кроме Anthropic API и Claude Platform on AWS, пока вы не задавали `CLAUDE_CODE_ENABLE_AUTO_MODE=1`; v2.1.207 убрал это требование. Переменная по-прежнему принимается для совместимости и с v2.1.207 не действует.
- **Классификатор**: добавляет расход токенов, кроме планов Enterprise и учётных записей Claude API, где v2.1.278+ выполняет проверку на стороне сервера бесплатно

### Включение режима Auto

```bash
# Интерактивные сессии стартуют в режиме Auto, если режим разрешений не задан (v2.1.284+)
# Чтобы выбрать его явно, например когда в настройках по умолчанию другой режим:
claude --permission-mode auto

# Или переключитесь на него через Shift+Tab в REPL
```

> **Обновление v2.1.112**: режиму Auto больше не нужен флаг `--enable-auto-mode`. Подписчики Max получают его напрямую на Opus 4.7.

> **Обновление v2.1.158**: режим Auto стал доступен на Bedrock, Vertex и Foundry для Opus 4.7/4.8 за флагом `CLAUDE_CODE_ENABLE_AUTO_MODE=1`.
>
> **Обновление v2.1.207**: это требование явного включения убрано. Режим Auto теперь доступен по умолчанию на Bedrock, Vertex AI, Microsoft Foundry и в сессиях шлюза приложений Claude со входом для Claude Sonnet 5, Opus 4.7, Opus 4.8 и Fable 5 (а также Opus 5 с v2.1.219) — флаг и переменная окружения не нужны. Администраторы могут отключить его через `disableAutoMode` в управляемых настройках. `CLAUDE_CODE_ENABLE_AUTO_MODE` по-прежнему принимается для совместимости, но с v2.1.207 не действует.

Или задайте его режимом разрешений по умолчанию:

```bash
claude --permission-mode auto
```

Настройка через конфиг:
```json
{
  "permissions": {
    "defaultMode": "auto"
  }
}
```

### Как работает классификатор

Фоновый классификатор оценивает каждое действие в таком порядке:

1. **Правила allow/deny** — сначала проверяются явные правила разрешений
2. **Чтение и правки одобряются автоматически** — чтение и правка файлов проходят сами
3. **Классификатор** — фоновый классификатор проверяет действие
4. **Запасной вариант** — после 3 блокировок подряд или 20 блокировок всего происходит возврат к запросу подтверждения

### Действия, блокируемые по умолчанию

Режим Auto по умолчанию блокирует следующее:

| Блокируемое действие | Пример |
|----------------------|--------|
| Установка через конвейер в оболочку | `curl \| bash` |
| Отправка чувствительных данных наружу | API-ключи, учётные данные по сети |
| Деплой в продакшен | Команды деплоя, нацеленные на продакшен |
| Массовое удаление | `rm -rf` в больших каталогах |
| Изменения IAM | Изменение разрешений и ролей |
| Force push в main | `git push --force origin main` |

> **Больше решений отдано классификатору (v2.1.218)**: классификатор также решает удаления, нацеленные на корень файловой системы или домашний каталог, например `rm -rf /` и `rm -rf ~`, в том числе когда удаление находится внутри подстановки команды или процесса. До v2.1.218 простые формы запрашивали одобрение, а формы с подстановкой запрашивали его в v2.1.208–v2.1.217. Проверки фонового `&` и подозрительных путей Windows тоже больше не открывают диалоги разрешений — их оценивает классификатор.

### Действия, разрешённые по умолчанию

| Разрешённое действие | Пример |
|----------------------|--------|
| Локальные операции с файлами | Чтение, запись и правка файлов проекта |
| Установка объявленных зависимостей | `npm install`, `pip install` из манифеста |
| HTTP только на чтение | `curl` для загрузки документации |
| Push в текущую ветку | `git push origin feature-branch` |

### Настройка режима Auto

**Вывести правила по умолчанию как JSON**:
```bash
claude auto-mode defaults
```

**Восстановить конфигурацию режима Auto по умолчанию** (v2.1.212), с запросом подтверждения (`--yes`, чтобы пропустить):
```bash
claude auto-mode reset
claude auto-mode reset --yes
```

**Настройте доверенную инфраструктуру** через управляемую настройку `autoMode.environment` для корпоративного деплоя. Так администраторы задают доверенные среды CI/CD, цели деплоя и шаблоны инфраструктуры.

#### Расширение значений по умолчанию через `"$defaults"` (v2.1.118)

С v2.1.118 `autoMode.allow`, `autoMode.soft_deny` и `autoMode.environment` принимают токен `"$defaults"`, который **добавляет** ваши правила к встроенному списку, а не заменяет его. До v2.1.118 любой заданный пользователем массив молча затирал встроенные правила.

#### Безусловные блокировки через `autoMode.hard_deny` (v2.1.136)

`autoMode.hard_deny` (v2.1.136+) — массив правил классификатора, которые блокируют класс действий **независимо от выведенного намерения пользователя**. Используйте его для действий, которые в режиме Auto не должны выполняться никогда, — например `rm -rf` по корневым путям или `git push --force` в защищённые ветки. В отличие от `soft_deny`, правила hard-deny классификатор не обсуждает.

```json
{
  "autoMode": {
    "hard_deny": ["Bash(rm -rf /:*)", "Bash(git push --force*)"]
  }
}
```

**Раньше (замена встроенных правил — поведение до v2.1.118):**

```json
{
  "autoMode": {
    "allow": ["Bash(gh pr list:*)"]
  }
}
```

**Теперь (расширение встроенных правил — v2.1.118+):**

```json
{
  "autoMode": {
    "allow": ["$defaults", "Bash(gh pr list:*)"],
    "soft_deny": ["$defaults", "Bash(kubectl delete:*)"],
    "environment": ["$defaults", "trusted-ci.internal"]
  }
}
```

Используйте `"$defaults"`, чтобы сохранить поставляемые базовые правила и сверху добавить правила организации или проекта.

#### Классификация каждой команды оболочки через `autoMode.classifyAllShell` (v2.1.193)

`autoMode.classifyAllShell` (логическое значение, v2.1.193+) направляет **все** команды Bash/PowerShell через классификатор режима Auto. Включите его, если классификатор должен проверять каждую команду оболочки в сессии.

```json
{
  "autoMode": {
    "classifyAllShell": true
  }
}
```

Тот же релиз показывает **причину отказа**, когда режим Auto блокирует действие, — в транскрипте, во всплывающем уведомлении об отказе и в списке недавних отказов в `/permissions` (v2.1.193+).

#### Встроенная защита на основе намерения (v2.1.183)

Отдельно от настроенного пользователем `hard_deny` режим Auto по умолчанию блокирует следующие разрушительные команды, если вы явно не просили их в этой сессии:

- `git reset --hard`, `git checkout -- .`, `git clean -fd`, `git stash drop`
- `git commit --amend` (если коммит в этой сессии сделал не агент)
- `terraform destroy`, `pulumi destroy`, `cdk destroy` (если вы не просили конкретный стек)

Это встроенная защита по умолчанию на основе выведенного намерения — добавлять эти команды в `hard_deny` самостоятельно не нужно.

### Поведение при возврате к запросу

Когда классификатор не уверен, режим Auto возвращается к запросу у пользователя:
- После **3 блокировок подряд** классификатором
- После **20 блокировок** классификатором за сессию

Так пользователь сохраняет контроль, когда классификатор не может уверенно одобрить действие.

### Начальные разрешения, эквивалентные режиму Auto

Если нужен более простой подход без фонового классификатора, заполните `~/.claude/settings.json` консервативным базовым набором безопасных правил разрешений. Скрипт начинает с правил только на чтение и локальный осмотр, а правки, тесты, локальную запись git, установку пакетов и действия записи GitHub вы включаете только когда они нужны.

**Файл:** `09-advanced-features/setup-auto-mode-permissions.py`

```bash
# Посмотреть, что будет добавлено (изменения не записываются)
python3 09-advanced-features/setup-auto-mode-permissions.py --dry-run

# Применить консервативную базу
python3 09-advanced-features/setup-auto-mode-permissions.py

# Добавлять возможности только когда они нужны
python3 09-advanced-features/setup-auto-mode-permissions.py --include-edits --include-tests
python3 09-advanced-features/setup-auto-mode-permissions.py --include-git-write --include-packages
```

Скрипт добавляет правила по таким категориям:

| Категория | Примеры |
|-----------|---------|
| Базовые инструменты только на чтение | `Read(*)`, `Grep(*)`, `Agent(*)`, `WebSearch(*)`, `WebFetch(*)` |
| Локальный осмотр | `Bash(git status:*)`, `Bash(git log:*)`, `Bash(git diff:*)`, `Bash(cat:*)` |
| Необязательные правки | `Edit(*)` |
| Необязательные тесты и сборка | `Bash(pytest:*)`, `Bash(python3 -m pytest:*)`, `Bash(cargo test:*)` |
| Необязательная запись git | `Bash(git add:*)`, `Bash(git commit:*)`, `Bash(git checkout:*)`, `Bash(git switch:*)`, `Bash(git stash:*)`, `Bash(git tag:*)` |
| Менеджеры пакетов | `Bash(npm ci:*)`, `Bash(npm install:*)`, `Bash(pip install:*)`, `Bash(pip3 install:*)` |
| Сборка и тесты | `Bash(make:*)`, `Bash(pytest:*)`, `Bash(go test:*)` |
| Обычная оболочка | `Bash(ls:*)`, `Bash(cat:*)`, `Bash(find:*)` |
| GitHub CLI | `Bash(gh pr view:*)`, `Bash(gh pr create:*)`, `Bash(gh issue list:*)` |

Опасные операции (`rm -rf`, `sudo`, force push, `DROP TABLE`, `terraform destroy` и т. п.) намеренно исключены. Скрипт идемпотентен — повторный запуск не дублирует правила.

## Фоновые задачи

Фоновые задачи позволяют выполнять долгие операции, не блокируя разговор.

### Что такое фоновые задачи?

Фоновые задачи идут асинхронно, пока вы продолжаете работу:
- Длинные наборы тестов
- Процессы сборки
- Миграции базы данных
- Скрипты деплоя
- Инструменты анализа

**Базовое использование:**
```bash
Пользователь: Запусти тесты в фоне

Claude: Запущена задача bg-1234

/tasks    # Просмотр и управление фоновой работой (оболочки и субагенты); отсюда же можно остановить задачу
Ctrl+B    # Перенести выполняющуюся команду Bash или агента в фон
```

### Запуск фоновых задач

```
Пользователь: Запусти полный набор тестов в фоне

Claude: Запускаю тесты в фоне (task-id: bg-1234)
Можно продолжать работу, пока тесты идут.

[Можно продолжать разговор]

Пользователь: А пока давай отрефакторим модуль аутентификации

Claude: [Работает над модулем аутентификации, пока тесты идут в фоне]

[Позже, когда тесты завершатся]

Claude: 📢 Фоновая задача bg-1234 завершена:
✅ 245 тестов прошли
❌ 3 теста упали
Результаты: /tasks
```

### Управление фоновыми задачами

Запустите `/tasks` (псевдоним `/bashes`), чтобы перечислить работающие оболочки и субагентов, открыть один из них и посмотреть вывод или остановить его. Подкоманд `/task` нет.

```text
Пользователь: /tasks

[Открывает представление фоновой работы: работающие оболочки и субагенты,
 включая субагентов, которые уже закончили. Выберите один, чтобы увидеть
 вывод, или остановите его отсюда.]
```

### Пример: параллельная разработка

```
Пользователь: Запусти сборку в фоне

Claude: Запускаю сборку... (task-id: bg-5001)

Пользователь: И линтер тоже в фоне

Claude: Запускаю линтер... (task-id: bg-5002)

Пользователь: Пока они работают, давай реализуем новую конечную точку API

Claude: [Реализует конечную точку API, пока идут сборка и линтер]

[Через 10 минут]

Claude: 📢 Сборка успешно завершена (bg-5001)
📢 Линтер нашёл 12 замечаний (bg-5002)

Пользователь: Покажи замечания линтера

Claude: [Показывает вывод линтера из bg-5002]
```

### Настройка

Блока в `settings.json` для фоновых задач нет. Функция управляется переменной окружения:

```bash
# Полностью выключить фоновые задачи
export CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=true
```

Параллелизм тоже не является настройкой фоновых задач — сколько агентов работает одновременно, задаёт `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` (по умолчанию `20`).

У фоновых команд Bash и PowerShell ограничение по времени есть только в необслуживаемых сессиях (v2.1.288): в запуске `-p`, сессии Agent SDK, CI или облачной сессии команда, запущенная с `run_in_background`, останавливается по своему `timeout` — по умолчанию 30 минут, максимум 2 часа — и Claude получает уведомление, когда команду остановили. У фоновых команд в терминале, настольном приложении или сессии VS Code ограничения по времени нет (в v2.1.285–v2.1.287 ограничение действовало на каждую сессию).

## Инструмент Monitor (потоки по событиям)

> **Новое в v2.1.98**: инструмент Monitor позволяет Claude следить за stdout фоновой команды и реагировать в момент, когда появляется подходящее событие, — вместо циклов опроса и `sleep` при ожидании долгих процессов.

Monitor подключается к любой команде оболочки, которая пишет в stdout. Каждая строка stdout команды становится уведомлением, которое будит сессию. Claude задаёт команду; обвязка транслирует вывод и доставляет события по мере появления. Запуск самих процессов описан в разделе [Фоновые задачи](#фоновые-задачи).

> **Дедлайны (v2.1.271)**: у каждого наблюдения Monitor теперь есть дедлайн — не больше 30 минут или 10 минут в однопромптовых запусках `-p`. Когда дедлайн проходит, Claude получает уведомление и может заново поставить наблюдение. Поставить наблюдение, которое никогда не истекает, больше нельзя.

### Почему это важно

Опрос через `/loop` или `sleep` тратит полный круг API на каждый цикл, изменилось что-то или нет. Monitor молчит, пока не сработает событие, и пока команда тиха, расходует **ноль токенов**. Когда событие происходит, Claude реагирует сразу — без запоздалого обнаружения в ожидании следующего тика опроса. Для всего, что длится дольше нескольких минут, это и дешевле, и быстрее циклов опроса.

### Два типичных паттерна

**Фильтры потока** следят за непрерывным выводом долгого источника. Команда работает бесконечно; каждая подходящая строка — событие.

```bash
tail -f /var/log/app.log | grep --line-buffered "ERROR"
```

**Фильтры «опроси и выведи»** периодически проверяют источник и выдают строку только когда что-то изменилось. Используйте их для API, баз данных и всего, у чего нет собственного потока.

```bash
last=$(date -u +%Y-%m-%dT%H:%M:%SZ)
while true; do
  gh api "repos/owner/repo/issues/123/comments?since=$last" || true
  last=$(date -u +%Y-%m-%dT%H:%M:%SZ)
  sleep 30
done
```

### Конкретный пример

«Запусти мой dev-сервер и следи за ошибками.» Claude запускает сервер как фоновую задачу, подключает фильтр Monitor (`tail -F server.log | grep --line-buffered -E "ERROR|FATAL"`), и сессия затихает. Как только в журнале появляется строка ошибки, Claude просыпается, читает ошибку и может среагировать — перезапустить сервер, исправить ошибку или показать её вам — вам не нужно проверять это самим.

> **Предупреждение**: при передаче в `grep` **всегда** используйте `grep --line-buffered`. Без этого grep буферизует stdout блоками по 4 КБ, и на малоактивных потоках события могут запаздывать на минуты. Это самый частый способ сломать Monitor на практике: если фильтр молчит, хотя не должен, сначала проверьте флаг `--line-buffered`.

## Динамические Workflows

> **Новое в v2.1.154**

Динамические Workflows позволяют Claude детерминированно оркестрировать от десятков до сотен фоновых [субагентов](../04-subagents/README.md) — fan-out, пайплайны и параллельные стадии закодированы в скрипте, а не оставлены импровизации модели. Там, где один агент держит одно контекстное окно, workflow раскладывает задачу на многих агентов и снова собирает их результаты.

С v2.1.219 у динамических Workflows по умолчанию **ориентир среднего размера (меньше 10 агентов)** — или **малый**, если вы вошли на плане Pro, с v2.1.271. Другой размер — или без ограничения — выбирается через **Dynamic workflow size** в `/config` или ключом `workflowSizeGuideline` в файле настроек. Строка состояния запущенного workflow показывает активный размер и ссылается на `/config`, где его можно изменить.

### Когда их использовать

- **Широкий охват** — аудит или ревью многих файлов и измерений параллельно.
- **Уверенность** — независимые точки зрения, затем состязательная проверка выводов до того, как фиксировать результат.
- **Масштаб больше одного контекста** — крупные миграции, широкие проходы или исследование, которое не помещается в один контекст.

Для разовой задачи, которую вы уже понимаете, по-прежнему уместен один агент (или прямая правка) — Workflows окупаются, когда работа расходится веером.

### Запуск и просмотр

- **Запуск**: попросите Claude создать workflow для задачи (например, «запусти workflow, чтобы проверить каждый файл в `src/`»). Claude пишет скрипт оркестрации и запускает его в фоне.
- **Просмотр**: команда `/workflows` показывает запущенные и завершённые прогоны workflow с живым прогрессом.
- **`ultracode`**: включите переключателем Ultracode на ползунке `/effort` (Tab) или командой `/effort ultracode [on|off]` — тогда Claude по умолчанию оркестрирует динамические Workflows на том уровне усилия, на котором идёт сессия. С v2.1.284 переключатель не меняет уровень усилия (раньше он принудительно ставил `xhigh`); `--effort ultracode` и `effortLevel: "ultracode"` в Agent SDK по-прежнему ставят `xhigh`. `/effort ultracode` действует на время сессии; чтобы начинать каждую сессию с ним, задайте ключ `ultracode` в настройках (`effortLevel` и `CLAUDE_CODE_EFFORT_LEVEL` не принимают `ultracode`). (С v2.1.160 ключевое слово-триггер — `ultracode`; голое слово «workflow» больше не запускает прогон.)

Workflows опираются на модель субагентов — как задаются и ограничиваются отдельные агенты, см. в [Субагенты](../04-subagents/README.md).

## Запланированные задачи

Запланированные задачи запускают промпты автоматически по расписанию или как одноразовые напоминания. Задачи привязаны к сессии: они выполняются, пока Claude Code активен, и очищаются, когда сессия заканчивается. Доступны с v2.1.72+.

> **На claude.com с 2026-05-14 это называется «Routines»**: блог продукта Anthropic представляет эту поверхность как **Routines**. Команда CLI остаётся `/schedule`; в этом руководстве для непрерывности используется исходное название «Запланированные задачи». Если в документации claude.com или в настольном приложении вы видите «Routines», речь о той же функции.

### Команда `/loop`

```bash
# Явный интервал
/loop 5m проверь, завершился ли деплой

# Естественный язык
/loop проверяй статус сборки каждые 30 минут
```

Для точного расписания также поддерживаются стандартные cron-выражения из 5 полей.

### Одноразовые напоминания

Напоминания, которые срабатывают один раз в заданное время:

```
напомни мне в 15:00 отправить ветку релиза
через 45 минут запусти интеграционные тесты
```

### Управление запланированными задачами

| Инструмент | Описание |
|------------|----------|
| `CronCreate` | Создать новую запланированную задачу |
| `CronList` | Перечислить все активные запланированные задачи. С v2.1.136 вывод также включает квалификаторы и тело запланированного промпта, чтобы проверить, что выполнит каждый cron, не открывая его. |
| `CronDelete` | Удалить запланированную задачу |

**Ограничения и поведение**:
- До **50 запланированных задач** на сессию
- Привязка к сессии — очищаются, когда сессия заканчивается
- Повторяющиеся задачи автоматически истекают через **3 дня**
- Задачи срабатывают, только пока Claude Code запущен, — пропущенные срабатывания не наверстываются

### Подробности поведения

| Аспект | Подробность |
|--------|-------------|
| **Джиттер повтора** | До 10% интервала (максимум 15 минут) |
| **Джиттер одноразового запуска** | До 90 секунд на границах :00/:30 |
| **Пропущенные срабатывания** | Без наверстывания — пропускаются, если Claude Code не был запущен |
| **Сохранение** | Не сохраняются между перезапусками |

### Облачные запланированные задачи

Через `/schedule` создаются облачные запланированные задачи, которые выполняются на инфраструктуре Anthropic:

```
/schedule ежедневно в 9:00 запускай набор тестов и сообщай о падениях
```

Облачные запланированные задачи сохраняются между перезапусками и не требуют, чтобы Claude Code был запущен локально.

### Отключение запланированных задач

```bash
export CLAUDE_CODE_DISABLE_CRON=1
```

> **`/schedule` автоматически отключается на тарифах с API-ключом (v2.1.139)**: облачный `/schedule` молча недоступен, если задан любой из `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` или `apiKeyHelper`, — даже если вы одновременно вошли через claude.ai. То же условие отключает [Remote Control](#отключение-remote-control-disableremotecontrol-v21128), MCP-коннекторы claude.ai и настройки уведомлений. Чтобы пользоваться `/schedule`, снимите API-ключ (или работайте на тарифе Pro/Max через OAuth). Локальный `CronCreate` не затрагивается.

### Пример: мониторинг деплоя

```
/loop 5m проверь статус деплоя среды staging.
        Если деплой прошёл, сообщи мне и прекрати цикл.
        Если он упал, покажи журналы ошибок.
```

> **Совет**: запланированные задачи привязаны к сессии. Для постоянной автоматизации, которая переживает перезапуски, используйте пайплайны CI/CD, GitHub Actions или запланированные задачи приложения Desktop.

## Режимы разрешений

Режимы разрешений определяют, какие действия Claude может выполнять без явного одобрения.

### Доступные режимы разрешений

| Режим | Поведение |
|---|---|
| `manual` | Только чтение файлов; для всех остальных действий запрос. Переименован из `default` в v2.1.200 — `default` по-прежнему принимается как псевдоним |
| `acceptEdits` | Чтение и правка файлов; для команд — запрос |
| `plan` | Только чтение файлов (режим исследования, без правок) |
| `auto` | Все действия с проверкой фоновым классификатором безопасности. Нужна подходящая модель (Sonnet 5 или новее, Opus 4.7 или новее, Haiku 5.5 либо модель Fable у любого провайдера; Opus 4.6 и Sonnet 4.6 также подходят на Anthropic API и Claude Platform on AWS) и провайдер — доступно на всех планах, см. [Режим Auto](#режим-auto) |
| `bypassPermissions` | Все действия, без проверок разрешений (опасно) |
| `dontAsk` | Выполняются только заранее одобренные инструменты; остальные отклоняются |

> **Примечание**: режим разрешений `default` переименован в **Manual** в v2.1.200 (в CLI, `--help`, VS Code и JetBrains), и пока он активен, в подвале показывается серый значок ⏸ (v2.1.203). Работают и `--permission-mode manual`, и `--permission-mode default`, а также `"defaultMode": "manual"` и `"defaultMode": "default"` в настройках. Ключ настройки — `permissions.defaultMode`; ключа `permissions.mode` нет, поэтому в примерах ниже каноническое написание.

Переключайте режимы через `Shift+Tab` в CLI. Режим по умолчанию задаётся флагом `--permission-mode` или настройкой `permissions.defaultMode`. Если режим разрешений не задан, интерактивные сессии терминала и VS Code с v2.1.284 стартуют в режиме Auto на каждом плане и у каждого провайдера (v2.1.283 делал это только на сторонних провайдерах, таких как Bedrock, Agent Platform от Google Cloud и Foundry, или при выключенной телеметрии); `permissions.defaultMode` по-прежнему перекрывает это, а сессия, где режим Auto недоступен, стартует в Manual. С v2.1.302 `claude -p` и сессии Agent SDK, в которых режим разрешений не задан, стартуют в режиме `default` на сторонних провайдерах, при выключенной телеметрии или на чистой установке; чтобы оставить режим Auto, передайте `--permission-mode auto`.

> **Режим планирования отдаёт команды оболочки классификатору (v2.1.218)**: когда [режим Auto](#режим-auto) доступен и настройка `useAutoModeDuringPlan` включена — а по умолчанию она включена — классификатор проверяет команды оболочки во время планирования, а не спрашивает вас. Одобренные команды выполняются, отклонённые блокируются. Запись в файлы режим планирования по-прежнему блокирует безусловно.

С v2.1.160 даже `acceptEdits` спрашивает перед записью файлов запуска оболочки (`.zshenv`, `.zlogin`, `.bash_login`, `~/.config/git/`) и конфигураций сборки, которые выполняют код (`.npmrc`, `.yarnrc*`, `bunfig.toml`, `.bazelrc`, `.pre-commit-config.yaml`, `.devcontainer/` и т. п.), иначе это могло бы привести к непреднамеренному выполнению команд.

> **Расширенное покрытие путей у `--dangerously-skip-permissions` (v2.1.121, v2.1.126)**: флаг CLI `--dangerously-skip-permissions` (и равнозначный режим `bypassPermissions`) теперь пропускает запросы для записи по гораздо более широкому списку — `.claude/skills/`, `.claude/agents/`, `.claude/commands/`, `.claude/`, `.git/`, `.vscode/` и файлы конфигурации оболочки. Катастрофические команды удаления (`rm -rf /` и т. п.) в этом режиме всё равно запрашивают подтверждение — с v2.1.281 этот запрос ждёт 2 минуты, затем отклоняет команду с подсказкой переписать её, чтобы необслуживаемые сессии продолжались (`CLAUDE_CODE_DISABLE_DANGEROUS_RM_TIMEOUT=1` это выключает) (в режиме Auto удаления по критическим путям уходят классификатору, а другие опасные формы `rm`, такие как `rm -rf "$(pwd)"`, всё ещё запрашивают подтверждение — см. [Режим Auto](#режим-auto)). Считайте флаг более острым инструментом, чем раньше; используйте его только в одноразовых песочницах.

> **Определение оболочки Windows (v2.1.120, v2.1.126)**: Git for Windows / Git Bash больше не обязателен. Если Git Bash нет, Claude Code использует PowerShell как инструмент оболочки. С v2.1.126 PowerShell — *основная* оболочка, когда инструмент PowerShell включён, а определение охватывает PowerShell 7, установленный через Microsoft Store, MSI без PATH или как глобальный инструмент `.NET`.

> **Инструмент PowerShell по умолчанию включён на Windows для Bedrock/Vertex/Foundry (v2.1.143)**: с v2.1.143 инструмент PowerShell **включён по умолчанию на Windows** для пользователей Bedrock, Vertex и Foundry. Claude Code вызывает PowerShell с `-ExecutionPolicy Bypass`, поэтому скрипты выполняются, даже если системная политика — `Restricted`. Чтобы Claude Code соблюдал системную политику выполнения, задайте `CLAUDE_CODE_POWERSHELL_RESPECT_EXECUTION_POLICY=1`. Чтобы полностью отключить инструмент PowerShell, задайте `CLAUDE_CODE_USE_POWERSHELL_TOOL=0`.

## Режим Headless

Режим print (`claude -p`) позволяет запускать Claude Code без интерактивного ввода — удобно для автоматизации и CI/CD. Это неинтерактивный режим, он заменяет прежний флаг `--headless`.

### Что такое режим print?

Режим print даёт:
- Автоматическое выполнение скриптов
- Интеграцию с CI/CD
- Пакетную обработку
- Запланированные задачи

### Запуск в режиме print (неинтерактивно)

```bash
# Выполнить конкретную задачу
claude -p "Запусти все тесты"

# Обработать содержимое из конвейера
cat error.log | claude -p "Проанализируй эти ошибки"

# Интеграция с CI/CD (GitHub Actions)
- name: AI-код-ревью
  run: claude -p "Проверь PR"
```

### Дополнительные примеры использования режима print

```bash
# Конкретная задача с захватом вывода
claude -p "Запусти все тесты и сформируй отчёт о покрытии"

# Со структурированным выводом
claude -p --output-format json "Проанализируй качество кода"

# С вводом из stdin
echo "Проанализируй качество кода" | claude -p "объясни это"
```

### Пример: интеграция с CI/CD

**GitHub Actions**:
```yaml
# .github/workflows/code-review.yml
name: AI-код-ревью

on: [pull_request]

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Установка Claude Code
        run: npm install -g @anthropic-ai/claude-code

      - name: Запуск код-ревью Claude Code
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          claude -p --output-format json \
            --max-turns 3 \
            "Проверь этот PR на:
            - Проблемы качества кода
            - Уязвимости безопасности
            - Вопросы производительности
            - Покрытие тестами
            Результат выведи как JSON" > review.json

      - name: Публикация комментария к ревью
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const review = JSON.parse(fs.readFileSync('review.json', 'utf8'));
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: JSON.stringify(review, null, 2)
            });
```

### Настройка режима print

Режим print (`claude -p`) поддерживает несколько флагов для автоматизации:

```bash
# Ограничить число автономных ходов
claude -p --max-turns 5 "отрефакторь этот модуль"

# Структурированный вывод JSON
claude -p --output-format json "проанализируй эту кодовую базу"

# С проверкой по схеме
claude -p --json-schema '{"type":"object","properties":{"issues":{"type":"array"}}}' \
  "найди ошибки в этом коде"

# Отключить сохранение сессии
claude -p --no-session-persistence "разовый анализ"
```

### Безопасный режим (диагностика)

`--safe-mode` (и переменная окружения `CLAUDE_CODE_SAFE_MODE`, например `CLAUDE_CODE_SAFE_MODE=1`) запускает Claude Code **со всеми отключёнными настройками** — CLAUDE.md, плагины, навыки, хуки и MCP-серверы выключены.

```bash
# Запуск со всеми отключёнными настройками
claude --safe-mode

# То же через переменную окружения
CLAUDE_CODE_SAFE_MODE=1 claude
```

Это инструмент диагностики: если пользовательская конфигурация вызывает проблемы, запустите безопасный режим, чтобы понять, дело в вашей настройке или в самом Claude Code.

## Управление сессиями

Эффективно управляйте несколькими сессиями Claude Code.

### Команды управления сессиями

| Команда | Описание |
|---------|----------|
| `/resume` | Возобновить разговор по ID или имени |
| `/rename` | Дать имя текущей сессии |
| `/fork [prompt]` | Скопировать разговор в новую независимую фоновую сессию и продолжить работу здесь (v2.1.212+) |
| `/subtask <task>` | Запустить форкнутого субагента, который наследует весь разговор и возвращает результат сюда (v2.1.212+) |
| `/branch [name]` | Переключиться в копию разговора с этой точки, сохранив оригинал |
| `claude -c` | Продолжить самый последний разговор |
| `claude -r "session"` | Возобновить сессию по имени или ID |

### Возобновление сессий

**Продолжить последний разговор**:
```bash
claude -c
```

**Возобновить именованную сессию**:
```bash
claude -r "auth-refactor" "доделай этот PR"
```

**Переименовать текущую сессию** (внутри REPL):
```
/rename auth-refactor
```

> **Обновление v2.1.212**: ввод `/resume` (без аргументов) в представлении агента теперь открывает выбор прошлых сессий — включая сессии, убранные из видимого списка, — и возобновляет выбранную как фоновую сессию.

### Форк и ветвление сессий

Три команды делают копии разговора, и они различаются тем, *где выполняется копия*:

`/subtask <task>` запускает форкнутого субагента, который наследует весь разговор и работает над задачей, пока вы продолжаете свою, — своя строка в `claude agents`, а результат возвращается в ваш разговор, когда субагент закончит:

```
/subtask Разберись, почему тесты аутентификации нестабильны
```

`/fork [prompt]` копирует разговор в новую **фоновую сессию**. Копия начинается со всего, что есть сейчас, и работает независимо — в этот разговор ничего не возвращается:

```
/fork Попробуй подход OAuth от начала до конца
```

Чтобы самому переключиться в копию, а не делегировать, используйте `/branch [name]`: оригинал сохраняется, и к нему можно вернуться через `/resume`:

```
/branch try-oauth-instead
```

> **Примечание**: `/fork` и `/subtask` поменялись ролями в **v2.1.212**. До v2.1.161 `/fork` был псевдонимом `/branch`; с v2.1.161 по v2.1.211 он запускал форкнутого субагента — это поведение теперь у `/subtask`. Когда представление агента выключено, `/subtask` недоступен, и `/fork` сохраняет поведение форкнутого субагента.

Или форк из CLI:
```bash
claude --resume auth-refactor --fork-session "попробуй OAuth"
```

### Сохранение сессий

Сессии сохраняются автоматически, и их можно возобновить:

```bash
# Продолжить последний разговор
claude -c

# Возобновить конкретную сессию по имени или ID
claude -r "auth-refactor"

# Возобновить и сделать форк для эксперимента
claude --resume auth-refactor --fork-session "альтернативный подход"
```

### Автопродолжение при лимите использования (v2.1.234)

С **v2.1.234** сессия, остановленная лимитом использования claude.ai, автоматически продолжается, когда лимит сбрасывается, — повторный промпт вручную не нужен. Переключается в `/config` пунктом «Continue automatically at usage limit».

### Сводка сессии (v2.1.108)

Когда вы возвращаетесь в сессию после отсутствия, Claude может показать краткую сводку того, что было сделано. Это включено по умолчанию для каждого плана и провайдера; выключается в `/config` → **Session recap**.

> **Телеметрия OTEL — снова включить опрос обратной связи (v2.1.136+)**: организации, которые собирают данные OpenTelemetry, могут снова включить опрос Anthropic о качестве сессии, задав `CLAUDE_CODE_ENABLE_FEEDBACK_SURVEY_FOR_OTEL=1`. В развёртываниях OTEL опрос по умолчанию выключен, потому что раньше он уводился в сторону от пайплайнов телеметрии.

> **Телеметрия OTEL — событие журнала `assistant_response` (v2.1.193+)**: Claude Code порождает событие журнала OpenTelemetry `claude_code.assistant_response` с текстом ответа модели, чтобы пайплайны OTEL фиксировали, что сказал Claude, рядом с уже существующей телеметрией инструментов и событий.

> **Телеметрия OTEL — атрибуты кэша и GenAI (v2.1.300)**: события `api_request` добавляют `cache_creation_5m_tokens`/`cache_creation_1h_tokens`, а спаны несут атрибуты семантических соглашений GenAI, например `gen_ai.provider.name`.

> **Телеметрия OTEL — атрибуты `tool_decision` (v2.1.301)**: события `tool_decision` добавляют `classifier_verdict` и `permission_mode`.

**Управление поведением сводки:**

```bash
/recap                                 # вручную вызвать сводку
/config                                # включить или выключить автосводку
```

Или через переменную окружения:
```bash
CLAUDE_CODE_ENABLE_AWAY_SUMMARY=0 claude   # отключить сводку
CLAUDE_CODE_ENABLE_AWAY_SUMMARY=1 claude   # принудительно включить сводку
```

## Обмен сообщениями между сессиями

> **Добавлено в v2.1.224**, расширено до v2.1.239. Доступно на **macOS, Linux и (с v2.1.239) Windows**.

Раньше сессии были островами. Обмен сообщениями между сессиями позволяет одной сессии Claude Code говорить с другой — включая сессии на других ваших машинах и облачные сессии, — чтобы передать вопрос той сессии, у которой уже загружен нужный контекст, а не объяснять всё заново.

### Обнаружение сессий

`ListAgents` перечисляет всё, к чему можно обратиться: субагентов, которых вы породили, другие локальные сессии на этой машине, ваши облачные сессии и (когда подключён Remote Control) сессии на других ваших машинах. Каждая строка помечена видом, а с v2.1.229 строки также несут метки `offline` и `cloud`, чтобы отличить достижимую сессию от спящей.

**Имя в каждой строке — это адрес**: именно его вы отправляете.

### Отправка сообщения

`SendMessage` принимает цель и сообщение:

```text
SendMessage({ to: "<имя сессии>", message: "К какому выводу вы пришли о логике повторных попыток?" })
```

С v2.1.232 достаточно голого имени — добавлять уточняющую ссылку больше не нужно, если только две строки действительно не носят одно и то же имя.

### Ожидание простоя сессии (`notify_when_idle`, v2.1.236)

Когда сессия, которой вы пишете, занята задачей, обычно нужно узнать, когда она закончит, а не опрашивать её. У `SendMessage` для этого есть вход `notify_when_idle`:

```text
SendMessage({
  to: "auth-refactor",
  message: "напишите мне, когда миграция закончится",
  notify_when_idle: true
})
```

Это **явное согласие и одноразовое действие**: целевая сессия присылает одно уведомление в следующий раз, когда перейдёт в простой, и на этом подписка заканчивается. Цикла опроса нет, и повторного уведомления нет, если сессия снова станет занятой и потом простой.

Два связанных изменения v2.1.239: `ListAgents` теперь также сообщает **собственное имя сессии** (чтобы сессия могла сказать другим, как к ней обращаться) рядом с живыми напарниками, а обмен сообщениями между сессиями стал доступен на **Windows**.

### Сокращение через `@`-упоминание (v2.1.232)

Вместо явного вызова инструмента можно упомянуть сессию через `@` прямо в промпте:

```text
@auth-refactor тесты миграции прошли?
```

### Управление входящими: `crossSessionInbound`

Входящие сообщения управляются настройкой `crossSessionInbound` (v2.1.224+):

| Значение | Поведение |
|---|---|
| `"accept"` | Входящие сообщения доставляются Claude в этой сессии |
| `"hold"` | вы видите уведомление, что сообщение пришло; оно не доставляется |
| `"refuse"` | Входящие сообщения отбрасываются |

Значения образуют лестницу — `accept < hold < refuse` — и **настройки проекта и локальные настройки применяются, только если они строже** значения области пользователя. Проект может ужесточить доставку входящих, но не ослабить её. С v2.1.232 у настройки также есть строка в `/config`: «Messages from your other sessions».

### Охват и ограничения

- Локальные сессии на той же машине плюс ваши облачные сессии.
- Сессии Remote Control на других ваших машинах, адресуемые по имени (v2.1.225).
- Облачная сессия **получает** ваше сообщение, но пока не может ответить локальной сессии — читайте её ответ в её собственном транскрипте.
- macOS и Linux с v2.1.224; Windows с v2.1.239.

Свои сочетания клавиш создаются командой `/keybindings`: она открывает `~/.claude/keybindings.json` для правки (v2.1.18+).

**Формат конфигурации**:

### Поддержка аккордов

Привязки поддерживают аккорды (сочетания из нескольких клавиш):

```
"ctrl+k ctrl+s"   → Последовательность из двух клавиш: нажмите ctrl+k, затем ctrl+s
"ctrl+shift+p"    → Одновременные клавиши-модификаторы
```

**Синтаксис нажатий**:
- **Модификаторы**: `ctrl` (или `control`), `alt` (или `opt`, `option`, `meta`), `shift` и `cmd` (или `command`, `super`, `win`) — `cmd` отдельный модификатор, не псевдоним `meta`, и определяется только в терминалах, которые сообщают клавишу Super
- **Верхний регистр подразумевает Shift**: `K` равносильно `shift+k`
- **Специальные клавиши**: `escape`, `enter`, `return`, `tab`, `space`, `backspace`, `delete`, клавиши-стрелки

### Режим Vim

Включите привязки Vi/Vim для правки текста:

**Активация**:
- Через `/config` (переключатель «Editor / Vim mode») или в `~/.claude/settings.json` ключом `editorMode: "vim"`. Отдельная слэш-команда `/vim` удалена (см. [issue #43370](https://github.com/anthropics/claude-code/issues/43370)); режим Vim теперь задаётся конфигурацией.
- Переключение режимов: `Esc` для NORMAL, `i/a/o` для INSERT, `v` для VISUAL, `V` для VISUAL-LINE (v2.1.118+)

**Клавиши навигации**:
- `h` / `l` — влево/вправо
- `j` / `k` — вниз/вверх
- `w` / `b` / `e` — по словам
- `0` / `$` — в начало/конец строки
- `gg` / `G` — в начало/конец текста
- `%` — к парной скобке; сочетается с `d`, `c`, `y` (v2.1.301)

**Текстовые объекты**:
- `iw` / `aw` — слово внутри/вокруг
- `i"` / `a"` — строка в кавычках внутри/вокруг
- `i(` / `a(` — круглые скобки внутри/вокруг

**Визуальные режимы (v2.1.118+)**:

| Клавиша | Режим | Поведение |
|---------|-------|-----------|
| `v` | Visual | Посимвольное выделение с визуальной обратной связью; расширяется клавишами движения |
| `V` | Visual-line | Построчное выделение; всегда выделяет строки целиком |
| `y` | Yank | Копировать текущее визуальное выделение |
| `d` / `x` | Delete | Удалить текущее визуальное выделение |
| `c` | Change | Удалить выделение и войти в режим INSERT |
| `Esc` | Exit | Вернуться в режим NORMAL |

Визуальные выделения подсвечиваются в поле ввода, чтобы до применения оператора было видно, что именно будет скопировано, удалено или изменено.

## Стили вывода

Стили вывода меняют **то, как** отвечает Claude, а не то, что он знает. Они изменяют системный промпт: роль, тон и формат ответа по умолчанию. Берите стиль, если каждый ход заново просите один и тот же голос или хотите, чтобы Claude выступал не как инженер-программист.

Инструкции о проекте или кодовой базе кладите в [CLAUDE.md](../02-memory) — это другой механизм с другими компромиссами.

### Встроенные стили

| Стиль | Поведение |
|-------|-----------|
| **Default** | Стандартный системный промпт, настроенный на эффективное выполнение задач программной инженерии |
| **Proactive** | Claude действует сразу и делает разумные предположения, а не останавливается на рутинных решениях. Указания по автономному выполнению сильнее, чем в режиме Auto, но режим разрешений **не** меняется — запросы разрешений вы по-прежнему видите |
| **Explanatory** | Добавляет учебные «Insights» между шагами: объясняет выбор реализации и паттерны кодовой базы |
| **Learning** | Совместное обучение на практике. Claude делится наблюдениями *и* оставляет маркеры `TODO(human)`, чтобы вы сами реализовали небольшие стратегические куски |
| **Concise** (v2.1.237) | Claude начинает с результата и пропускает преамбулу и повествование. Тщательность не меняется — убирается только обрамление вокруг ответа. Выберите в `/config` → Output style или задайте `"outputStyle": "Concise"` |

### Выбор стиля

Запустите `/config` и выберите **Output style** либо `/output-style <style>`, чтобы переключиться напрямую — без аргумента команда перечисляет доступные стили и помечает текущий. В обоих случаях выбор сохраняется в `.claude/settings.local.json`. Чтобы задать стиль без меню, правьте настройку напрямую:

```json
{
  "outputStyle": "Explanatory"
}
```

> **Примечание**: отдельная команда `/output-style` была объявлена устаревшей в v2.1.73 и удалена в v2.1.91, но **вернулась в v2.1.269** и работает в v2.1.278. Она действует в сессиях headless и Remote Control. `/config` и настройка `outputStyle` тоже продолжают работать.

Стиль вывода — часть системного промпта, который Claude Code читает один раз при старте сессии: изменения вступают в силу после `/clear` или в новой сессии.

### Пользовательские стили вывода

Пользовательский стиль — это файл Markdown с frontmatter, сохранённый на одном из трёх уровней:

- Пользователь: `~/.claude/output-styles/`
- Проект: `.claude/output-styles/`
- Управляемая политика: `.claude/output-styles/` внутри каталога управляемых настроек

Стили проекта загружаются из каждого `.claude/output-styles/` между рабочим каталогом и корнем репозитория. С v2.1.178, если во вложенных каталогах одно и то же имя стиля, побеждает ближайший к рабочему каталогу.

```markdown
---
name: Сначала диаграммы
description: Начинай каждое объяснение с диаграммы
keep-coding-instructions: true
---

Объясняя код, архитектуру или поток данных, начни с диаграммы Mermaid,
которая показывает структуру, а затем объясни текстом.
```

| Frontmatter | Назначение | По умолчанию |
|-------------|------------|--------------|
| `name` | Имя стиля, если это не имя файла | Берётся из имени файла |
| `description` | Показывается в выборе `/config` | Нет |
| `keep-coding-instructions` | Сохранить встроенные инструкции Claude Code по программной инженерии | `false` |
| `force-for-plugin` | Только стили плагина: применять автоматически, когда плагин включён, перекрывая `outputStyle` пользователя | `false` |

**Задайте `keep-coding-instructions: true`**, если вы меняете то, как Claude общается, но хотите, чтобы он писал код по-прежнему. Опустите поле, если Claude вообще не занимается программной инженерией — например, это помощник по текстам или аналитик данных.

### Область действия и стоимость

Стили вывода применяются **только к основному разговору**. У субагента свой системный промпт, поэтому стили не меняют ответы субагентов; исключение — форк, потому что он наследует полный системный промпт родителя.

Дополнительные инструкции увеличивают входные токены, хотя кэш промптов поглощает большую часть этого после первого запроса. Explanatory и Learning по замыслу дают более длинные ответы, что увеличивает выходные токены.

### Сравнение с другими механизмами

| Функция | Как работает | Когда использовать |
|---------|--------------|--------------------|
| Стили вывода | Меняют системный промпт | Нужны другая роль, тон или формат на каждом ходе |
| [CLAUDE.md](../02-memory) | Добавляет сообщение пользователя после системного промпта | Claude всегда должен знать соглашения проекта |
| `--append-system-prompt` | Дописывает к системному промпту, ничего не убирая | Разовое добавление для одного вызова |
| [Субагенты](../04-subagents) | Работают со своим системным промптом, моделью и инструментами | Нужен помощник с отдельной областью |
| [Навыки](../03-skills) | Загружают инструкции под задачу при вызове | Есть повторно используемый рабочий процесс |

## Строка состояния

Строка состояния — это своя команда, чей вывод рисуется внизу сессии. Настройте её через `/statusline` или задайте напрямую:

```json
{
  "statusLine": {
    "type": "command",
    "command": "~/.claude/statusline.sh",
    "padding": 0
  }
}
```

`padding` по умолчанию равен `0`. Claude Code передаёт команде объект JSON на stdin, и скрипт сам решает, что показать.

### Доступные входные поля

| Группа | Поля |
|--------|------|
| Сессия | `session_id`, `session_name`, `prompt_id`, `transcript_path`, `cwd`, `version` |
| Модель | `model.id`, `output_style.name`, `effort.level`, `fast_mode`, `thinking.enabled` |
| Агент | `agent.name`, `vim.mode` |
| Стоимость | `cost.total_cost_usd`, `cost.total_duration_ms`, `cost.total_api_duration_ms`, `cost.total_lines_added` |
| Контекст | `context_window.context_window_size`, `.current_usage`, `.remaining_percentage`, `.total_input_tokens`, `.used_percentage` |
| Лимиты | `rate_limits.five_hour.used_percentage`, `.resets_at` |
| Репозиторий | `pr.number`, `pr.review_state`, `workspace.project_dir`, `workspace.added_dirs`, `workspace.git_worktree`, `workspace.repo.host` |
| Worktree | `worktree.name`, `.branch`, `.path`, `.original_branch`, `.original_cwd` |

### Пример

```bash
#!/bin/bash
# ~/.claude/statusline.sh — модель, использование контекста и стоимость
input=$(cat)
model=$(echo "$input" | jq -r '.model.id')
used=$(echo "$input" | jq -r '.context_window.used_percentage')
cost=$(echo "$input" | jq -r '.cost.total_cost_usd')
printf '%s | конт. %.0f%% | $%.2f' "$model" "$used" "$cost"
```

> **Примечание**: `statusLine` требует доверия к рабочей области. Скрипты строки состояния также получают `COLUMNS` и `LINES` в своём окружении (v2.1.153+), чтобы подгонять вывод под терминал.

## Режим TUI (полноэкранный)

> **Новое в v2.1.110**

Режим TUI (текстовый пользовательский интерфейс) рисует Claude Code на весь экран без мерцания — удобно для мультиплексоров терминала вроде tmux или разделённых панелей iTerm2.

### Включение режима TUI

Переключайте отрисовщики командой `/tui` или задайте `CLAUDE_CODE_NO_FLICKER=1` до запуска:

```bash
/tui fullscreen               # переключиться на полный экран из сессии
/tui default                  # вернуться к классической отрисовке
CLAUDE_CODE_NO_FLICKER=1 claude  # сразу стартовать на полном экране
```

### Настройка

| Настройка | Описание | По умолчанию |
|-----------|----------|--------------|
| `autoScrollEnabled` | Автопрокрутка к последнему сообщению | `true` |

Отключите автопрокрутку через `/config` или `settings.json`:

```json
{
  "autoScrollEnabled": false
}
```

### Режим фокуса

Команда `/focus` переключает режим фокуса — спокойный экран, где виден только самый важный вывод. `Ctrl+O` теперь переключает только обычный и подробный транскрипт (режим фокуса — это `/focus`).

## Каналы

Каналы — функция Research Preview: события из внешних сервисов попадают в запущенную сессию Claude Code через MCP-серверы. Источники включают Telegram, Discord, iMessage и произвольные вебхуки, поэтому Claude реагирует на уведомления в реальном времени без опроса.

> **Аутентификация (v2.1.128+)**: `--channels` теперь работает и с OAuth Pro/Max, **и** с аутентификацией по API-ключу (console). В более ранних релизах требовался OAuth.

### Подписка на каналы

```bash
# Подписаться на плагин канала при запуске
claude --channels plugin:telegram@claude-plugins-official

# Подписаться на несколько источников (через пробел)
claude --channels plugin:discord@claude-plugins-official plugin:telegram@claude-plugins-official
```

### Поддерживаемые интеграции

| Интеграция | Описание |
|------------|----------|
| **Discord** | Получать сообщения Discord и отвечать на них в сессии |
| **Telegram** | Получать сообщения Telegram и отвечать на них в сессии |
| **iMessage** | Получать уведомления iMessage в сессии |
| **Вебхуки** | Получать события из произвольных источников вебхуков |

### Настройка

Каналы настраиваются флагом `--channels` при запуске. Для корпоративного деплоя управляемая настройка задаёт, какие плагины каналов разрешены:

```json
{
  "channelsEnabled": true,
  "allowedChannelPlugins": [
    { "marketplace": "claude-plugins-official", "plugin": "discord" },
    { "marketplace": "claude-plugins-official", "plugin": "telegram" }
  ]
}
```

Управляемая настройка `allowedChannelPlugins` определяет, какие плагины каналов разрешены в организации. Она заменяет список допуска, который ведёт Anthropic, и требует `channelsEnabled: true`.

### Как это работает

1. MCP-серверы выступают плагинами каналов и подключаются к внешним сервисам
2. Входящие сообщения и события отправляются в активную сессию Claude Code
3. Claude может читать сообщения и отвечать на них в контексте сессии
4. Плагины каналов должны быть в списке допуска, который ведёт Anthropic, или в списке `allowedChannelPlugins` организации, если администратор его задал
5. Опрос не нужен — события приходят в реальном времени

## Интеграция с Chrome

Интеграция с Chrome соединяет Claude Code с браузером Chrome или Microsoft Edge для живой веб-автоматизации и отладки. Это бета-функция, доступная с v2.0.73+ (нужно расширение Claude in Chrome v1.0.36+).

### Включение интеграции с Chrome

**При запуске**:

```bash
claude --chrome      # Включить соединение с Chrome
claude --no-chrome   # Выключить соединение с Chrome
```

**Внутри сессии**:

```
/chrome
```

Выберите «Enabled by default», чтобы включить интеграцию с Chrome для всех будущих сессий. Claude Code использует состояние входа вашего браузера, поэтому может работать с веб-приложениями, где вы уже аутентифицированы.

> **Примечание**: с v2.1.290 файлы настроек проекта не могут включить интеграцию с Chrome — используйте `--chrome`, `/chrome` или пользовательские настройки.

### Возможности

| Возможность | Описание |
|-------------|----------|
| **Живая отладка** | Читать журналы консоли, осматривать элементы DOM, отлаживать JavaScript в реальном времени |
| **Проверка дизайна** | Сравнивать отрисованные страницы с макетами |
| **Проверка форм** | Тестировать отправку форм, проверку ввода и обработку ошибок |
| **Тестирование веб-приложений** | Взаимодействовать с приложениями, где вы уже вошли (Gmail, Google Docs, Notion и т. п.) |
| **Извлечение данных** | Собирать и обрабатывать содержимое веб-страниц |
| **Запись сессии** | Записывать действия в браузере как файлы GIF |

### Разрешения на уровне сайтов

Расширение Chrome управляет доступом по сайтам. Доступ к конкретным сайтам можно выдать или отозвать в любой момент через всплывающее окно расширения. Claude Code работает только с сайтами, которые вы явно разрешили.

### Как это работает

Claude Code управляет браузером в видимом окне — действия можно смотреть в реальном времени. Если браузер встречает страницу входа или CAPTCHA, Claude останавливается и ждёт, пока вы обработаете это вручную, и только потом продолжает.

### Известные ограничения

- **Поддержка браузеров**: Chrome и Edge; Claude Code также подключается в других браузерах на Chromium, таких как Brave, Arc, Vivaldi и Opera
- **WSL**: недоступно в подсистеме Windows для Linux (Windows Subsystem for Linux)
- **Сторонние провайдеры**: не поддерживается с провайдерами API Bedrock, Vertex и Foundry
- **Простой service worker**: service worker расширения Chrome может уйти в простой во время долгих сессий

> **Совет**: интеграция с Chrome — бета-функция. Поддержка браузеров может расшириться в будущих релизах.

## Remote Control

Remote Control позволяет продолжить локально запущенную сессию Claude Code с телефона, планшета или любого браузера. Локальная сессия продолжает работать на вашей машине — в облако ничего не переезжает. Доступно на планах Pro, Max, Team и Enterprise (v2.1.51+).

Remote Control **больше не является research preview** — метку убрали на 34-й неделе 2026 года. Любая машина, на которой запущен `claude remote-control`, теперь показывается как **карточка устройства** на вкладке Code в приложении Claude, поэтому сессию на этой машине можно начать прямо с телефона, а не сначала запускать её на машине и только потом подключаться.

### Запуск Remote Control

**Из CLI**:

```bash
# Запуск с именем сессии по умолчанию
claude remote-control

# Запуск с собственным именем
claude remote-control --name "Auth Refactor"
```

**Из сессии**:

```
/remote-control
/remote-control "Auth Refactor"
```

**Доступные флаги**:

| Флаг | Описание |
|------|----------|
| `--name "title"` | Свой заголовок сессии, чтобы её было проще узнать |
| `--verbose` | Показать подробные журналы соединения |

> **Примечание (v2.1.300)**: `claude remote-control` больше не принимает `--sandbox` и `--no-sandbox` (они никогда не действовали; передача любого из них теперь завершается с ошибкой). Чтобы поместить сессии Remote Control в песочницу, задайте `sandbox.enabled` в файле настроек.

### Подключение к сессии

Три способа подключиться с другого устройства:

1. **URL сессии** — печатается в терминал при старте сессии; откройте в любом браузере
2. **QR-код** — после запуска нажмите `spacebar`, чтобы показать QR-код для сканирования
3. **Поиск по имени** — просмотрите сессии на claude.ai/code или в мобильном приложении Claude (iOS/Android)

### Безопасность

- **Входящие порты не открываются** на вашей машине
- **Только исходящий HTTPS** поверх TLS
- **Ограниченные учётные данные** — несколько короткоживущих токенов узкой области
- **Изоляция сессий** — каждая удалённая сессия независима

### Remote Control в сравнении с Claude Code в вебе

| Аспект | Remote Control | Claude Code в вебе |
|--------|----------------|--------------------|
| **Выполнение** | На вашей машине | В облаке Anthropic |
| **Локальные инструменты** | Полный доступ к локальным MCP-серверам, файлам и CLI | Локальных зависимостей нет |
| **Сценарий** | Продолжить локальную работу с другого устройства | Начать с нуля из любого браузера |

### Ограничения

- Одна удалённая сессия на интерактивный процесс Claude Code — серверный режим (`claude remote-control`) обслуживает несколько сразу (`--capacity`, по умолчанию 32)
- Терминал на машине-хосте должен оставаться открытым
- Если сеть недоступна, серверный режим завершается примерно через 10 минут; интерактивная сессия продолжает повторять попытки и переподключается, когда сеть возвращается

### Сценарии использования

- Управлять Claude Code с телефона или планшета, когда вы не за столом
- Пользоваться более богатым интерфейсом claude.ai, сохраняя локальное выполнение инструментов
- Быстрое код-ревью на ходу с полным локальным окружением разработки

### Push-уведомления (v2.1.110)

Когда Remote Control активен и в `/config` включено «Push when Claude decides», Claude может отправлять мобильные push-уведомления на телефон — например, когда долгая задача завершилась или нужен ваш ввод.

Чтобы включить:
1. Активируйте Remote Control: `/remote-control` или `claude --rc`
2. Откройте `/config` и включите **Push when Claude decides**

Для push-уведомлений нужны подписка Claude и мобильное приложение Claude.

### Отключение Remote Control (`disableRemoteControl`, v2.1.128+)

Администраторы планов Team или Enterprise могут полностью заблокировать Remote Control настройкой `disableRemoteControl`. Когда значение `true`, и `claude remote-control`, и `/remote-control` отказываются запускаться.

```json
{
  "disableRemoteControl": true
}
```

Настройка соблюдается в области **managed/policy** (например, `/Library/Application Support/ClaudeCode/managed-settings.json` на macOS), поэтому отдельные пользователи не могут её перекрыть. Полезно, когда во всей организации нужно принудительно оставить только локальное выполнение.

> **Когда Remote Control автоматически отключается на тарифах с API-ключом (v2.1.139)**: Remote Control **молча отключается**, если задан любой из этих параметров, даже если вы одновременно вошли через claude.ai:
>
> - `ANTHROPIC_API_KEY`
> - `ANTHROPIC_AUTH_TOKEN`
> - `apiKeyHelper` (settings.json)
>
> То же условие отключает [`/schedule`](#запланированные-задачи), MCP-коннекторы claude.ai и настройки уведомлений — все четыре поверхности, связанные с claude.ai, открыты только когда активные учётные данные — это вход через OAuth. Чтобы пользоваться этими функциями, снимите API-ключ (или работайте на тарифе Pro/Max через OAuth).

## Веб-сессии

Веб-сессии позволяют запускать Claude Code прямо в браузере на claude.ai/code или создавать веб-сессии из CLI.

### Создание веб-сессии

```bash
# Создать новую веб-сессию из CLI
claude --remote "реализуй новые конечные точки API"
```

Так запускается сессия Claude Code на claude.ai, доступная из любого браузера.

### Возобновление веб-сессий локально

Если сессия начата в вебе и её нужно продолжить локально:

```bash
# Возобновить веб-сессию в локальном терминале — открывает выбор ваших веб-сессий
claude --teleport
```

Или из интерактивного REPL:

```text
/teleport
```

`/tp` — псевдоним `/teleport`. Оба требуют подписку claude.ai. Облачные сессии
показывают подсказку `/teleport` с объяснением, как продолжить локально (v2.1.223).

> **По данным журнала изменений**: журнал v2.1.223 показывает форму с аргументом,
> `claude --teleport <session id>`, которая сразу переходит к известной сессии. Справочник CLI
> документирует только форму с выбором без аргумента, поэтому предпочитайте `claude --teleport`, если
> ID сессии у вас ещё нет.

### Сценарии использования

- Начать работу на одной машине и продолжить на другой
- Поделиться URL сессии с коллегами
- Просмотреть diff в веб-интерфейсе, затем переключиться в терминал для выполнения

## Приложение Desktop

Настольное приложение Claude Code Desktop — отдельное приложение с визуальным просмотром diff, параллельными сессиями и встроенными коннекторами. Доступно для macOS и Windows (планы Pro, Max, Team и Enterprise).

### Установка

Скачайте с [claude.ai](https://claude.ai) для своей платформы:
- **macOS**: универсальная сборка (Apple Silicon и Intel)
- **Windows**: доступны установщики x64 и ARM64

Инструкции по установке — в [Desktop Quickstart](https://code.claude.com/docs/en/desktop-quickstart).

### Передача из CLI

Перенесите текущую сессию CLI в приложение Desktop:

```
/desktop
```

### Основные функции

| Функция | Описание |
|---------|----------|
| **Просмотр diff** | Визуальная проверка файл за файлом со встроенными комментариями; Claude читает комментарии и правит |
| **Предпросмотр приложения** | Сам запускает dev-серверы со встроенным браузером для живой проверки |
| **Мониторинг PR** | Интеграция с GitHub CLI: автоисправление падений CI и автослияние, когда проверки проходят |
| **Параллельные сессии** | Несколько сессий на боковой панели с автоматической изоляцией Git worktree |
| **Запланированные задачи** | Повторяющиеся задачи (ежечасно, ежедневно, по будням, еженедельно), которые идут, пока приложение открыто |
| **Богатая отрисовка** | Отрисовка кода, markdown и диаграмм с подсветкой синтаксиса; флажки списков задач GitHub-Flavored Markdown (`- [ ]` / `- [x]`) рисуются как флажки (v2.1.149+) |

### Настройка предпросмотра приложения

- **Удалённые сессии**: выполняются на облачной инфраструктуре Anthropic и продолжаются, даже когда приложение закрыто. Доступны с claude.ai/code или из мобильного приложения Claude

- **Деплой через MDM**: деплой через MDM на macOS или MSIX на Windows

## Список задач

Список задач даёт постоянное отслеживание задач, которое переживает сжатия контекста (когда история разговора обрезается, чтобы поместиться в контекстное окно).

### Переключение списка задач

Нажмите `Ctrl+T`, чтобы включить или выключить представление списка задач во время сессии.

### Постоянные задачи

Задачи сохраняются между сжатиями контекста, поэтому долгие пункты работы не теряются, когда контекст разговора обрезается. Это особенно полезно для сложных многошаговых реализаций.

### Именованные каталоги задач

Переменная окружения `CLAUDE_CODE_TASK_LIST_ID` создаёт именованные каталоги задач, общие для сессий:

```bash
export CLAUDE_CODE_TASK_LIST_ID=my-project-sprint-3
```

Так несколько сессий делят один список задач — удобно для командных рабочих процессов и проектов с несколькими сессиями.

## Git Worktrees

Git worktree позволяют запустить Claude Code в изолированном worktree и параллельно работать над разными ветками, не пряча изменения в stash и не переключаясь.

### Запуск в worktree

```bash
# Запустить Claude Code в изолированном worktree
claude --worktree
# или
claude -w
```

### Расположение worktree

Worktree создаются здесь:
```
<repo>/.claude/worktrees/<name>
```

### Sparse checkout для монорепозиториев

Настройка `worktree.sparsePaths` делает sparse checkout в монорепозиториях и сокращает расход диска и время клонирования:

```json
{
  "worktree": {
    "sparsePaths": ["packages/my-package", "shared/"]
  }
}
```

### Базовая ветка (`worktree.baseRef`)

**`worktree.baseRef`** (добавлено в v2.1.133) — откуда ветвится `claude --worktree`: от `origin/<default>` или от локального `HEAD`.

- `"fresh"` (по умолчанию) — ветка от `origin/<default-branch>`, локальные не отправленные коммиты игнорируются. **Это откатывает поведение, введённое в v2.1.128**, поэтому тем, кто после v2.1.128 полагался на ветвление от локального HEAD, нужно явно включить его обратно.
- `"head"` — ветка от локального `HEAD`, не отправленные коммиты сохраняются.

Задаётся в `~/.claude/settings.json`:

```json
{ "worktree": { "baseRef": "head" } }
```

### Изоляция фоновых сессий (`worktree.bgIsolation`)

**`worktree.bgIsolation`** (добавлено в v2.1.143) — получают ли фоновые сессии (например, из `/bg`, `claude --bg` или Agent View) собственный worktree или правят переднюю рабочую копию напрямую.

- *(по умолчанию)* — фоновые сессии создают изолированный worktree в `<repo>/.claude/worktrees/`, так же, как `--worktree`.
- `"none"` — фоновые сессии правят текущую рабочую копию напрямую. Используйте это, когда worktree неудобны (например, тяжёлые артефакты нативной сборки) или когда фоновый агент должен согласовывать правки с передней сессией.

```json
{ "worktree": { "bgIsolation": "none" } }
```

Компромисс: `"none"` убирает страховку изоляции worktree — одновременные правки фоновой и передней сессий могут дать конфликты слияния в живой рабочей копии.

### Инструменты и хуки worktree

| Элемент | Описание |
|---------|----------|
| `EnterWorktree` | Инструмент входа в worktree; с v2.1.157 может переключаться между worktree под управлением Claude посреди сессии |
| `ExitWorktree` | Инструмент выхода и очистки текущего worktree |
| `WorktreeCreate` | Событие хука при создании worktree |
| `WorktreeRemove` | Событие хука при удалении worktree |

С v2.1.157 worktree под управлением Claude остаются разблокированными, когда агент заканчивает, поэтому `git worktree remove`/`prune` могут их убрать.

### Автоочистка

Если в worktree не было изменений, он автоматически очищается в конце сессии.

### Сценарии использования

- Работать над веткой функции, не трогая основную ветку
- Запускать тесты изолированно, не затрагивая рабочий каталог
- Пробовать экспериментальные изменения в одноразовой среде
- Делать sparse checkout конкретных пакетов в монорепозиториях для более быстрого старта

## Песочница

Песочница даёт изоляцию файловой системы и сети на уровне ОС для команд Bash, которые выполняет Claude Code. Это дополняет правила разрешений и добавляет ещё один слой безопасности.

### Включение песочницы

**Слэш-команда** (сохраняет выбор в `.claude/settings.local.json` для этого проекта):
```text
/sandbox
```

**Файл настроек** (все проекты): задайте `"sandbox": { "enabled": true }` в `~/.claude/settings.json`.

**На одну сессию**, не записывая файл настроек:
```bash
claude --settings '{"sandbox": {"enabled": true}}'
```

> Флагов `claude --sandbox` / `--no-sandbox` нет. С v2.1.300 их передача в `claude remote-control` завершается с ошибкой.

### Параметры конфигурации

| Настройка | Описание |
|-----------|----------|
| `sandbox.enabled` | Включить или выключить песочницу |
| `sandbox.failIfUnavailable` | Завершиться с ошибкой, если песочницу нельзя активировать |
| `sandbox.filesystem.allowWrite` | Пути, куда разрешена запись |
| `sandbox.filesystem.allowRead` | Пути, откуда разрешено чтение |
| `sandbox.filesystem.denyRead` | Пути, откуда чтение запрещено |
| `sandbox.network.allowedDomains` | Домены, до которых могут доходить процессы, запущенные из Bash (поддерживается подстановка `*.`) |
| `sandbox.network.deniedDomains` | Домены, которые блокируются, даже если подстановка `allowedDomains` иначе их разрешила бы (v2.1.113+) |
| `sandbox.network.strictAllowlist` | (v2.1.219) Запрещать хосты вне списка допуска для команд в песочнице без запроса |
| `sandbox.enableWeakerNetworkIsolation` | Включить более слабую сетевую изоляцию на macOS |
| `sandbox.bwrapPath` | (v2.1.133+, Linux/WSL) Путь к двоичному файлу `bubblewrap`. По умолчанию: поиск в `$PATH`. |
| `sandbox.socatPath` | (v2.1.133+, Linux/WSL) Путь к двоичному файлу `socat`. По умолчанию: поиск в `$PATH`. |
| `sandbox.credentials` | (v2.1.187+) Запретить командам в песочнице читать файлы учётных данных и секретные переменные окружения. |
| `sandbox.allowAppleEvents` | (v2.1.181+, macOS) Явно разрешить командам в песочнице отправлять Apple Events. |
| `sandbox.filesystem.disabled` | (v2.1.216+) Полностью пропустить изоляцию файловой системы, сохранив сетевую изоляцию — полезно, когда файловая песочница ломает инструменты, а контроль исходящей сети должен остаться. Учитывается только из пользовательских настроек, управляемых настроек или `--settings`; настройки проекта задать это не могут. |

**Пути к двоичным файлам Linux/WSL** (v2.1.133+) — укажите Claude Code нестандартные места установки:

```json
{
  "sandbox": {
    "bwrapPath": "/opt/bubblewrap/bin/bwrap",
    "socatPath": "/opt/socat/bin/socat"
  }
}
```

Пример, как `deniedDomains` перекрывает широкую подстановку (v2.1.113+):

```json
{
  "sandbox": {
    "network": {
      "allowedDomains": ["*.example.com"],
      "deniedDomains": ["evil.example.com"]
    }
  }
}
```

Подстановка пропускает всё на `example.com`, но `deniedDomains` всё равно блокирует явно названный хост.

> **Примечание** (v2.1.243): запрос разрешения у инструмента Bash в песочнице **больше не перечисляет разрешённые сетевые хосты**. Claude просто пытается выполнить запрос, и вы одобряете каждый новый хост по мере появления — не ждите, что запрос заранее покажет список допуска. Тот же релиз перестал отбрасывать подробности нарушения сети, когда заблокированная команда случайно завершается с кодом `0`, поэтому внешне тихий успех всё равно сообщает, что было заблокировано.

### Маскирование учётных данных (v2.1.221, v2.1.224)

> **По данным журнала изменений**: эти параметры `sandbox.credentials` взяты из записей
> журнала v2.1.221 и v2.1.224; справочник настроек их пока не описывает.

До v2.1.221 `sandbox.credentials` мог только `deny` файл учётных данных — команда в песочнице, которой эти данные были нужны, просто падала. `mode: "mask"` оставляет команду рабочей
и не раскрывает секрет: процесс в песочнице читает **сторожевую** копию файла,
а прокси песочницы подставляет настоящее значение на выходе в сеть.

```json
{
  "sandbox": {
    "network": { "tlsTerminate": true },
    "credentials": {
      "files": [
        { "path": "~/.aws/credentials", "mode": "mask" }
      ]
    }
  }
}
```

| Возможность | С версии | Что делает |
|---|---|---|
| `mode: "mask"` для **файлов** учётных данных | v2.1.221 | Команды в песочнице читают сторожевое значение; прокси подставляет настоящее на выходе. **Только Linux и WSL** — на macOS маскирование файлов откатывается к `deny`. |
| `extract` / `onExtractNoMatch` | v2.1.224 | Маскировать одно поле внутри структурированного значения окружения, а не всю переменную, и решить, что делать, если шаблон не совпал. |
| `decode: "jwt"` с `maskClaims` | v2.1.224 | Декодировать JWT и маскировать только названные claims, оставив остальное читаемым. |
| `awsPairs` / `sigv4` | v2.1.224 | Заново подписать запросы AWS SigV4 на прокси после подстановки настоящего ключа доступа. |

**Два ограничения, которые легко пропустить:**

- Любое маскирование требует `network.tlsTerminate` — прокси должен видеть внутренность запроса,
  чтобы подставить значение.
- Эти параметры учитываются **только** из пользовательских настроек, управляемых настроек или `--settings`.
  Настройки проекта не могут включить маскирование или изменить то, что маскируется.

### Пример конфигурации

```json
{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "filesystem": {
      "allowWrite": ["/Users/me/project"],
      "allowRead": ["/Users/me/project", "/usr/local/lib"],
      "denyRead": ["/Users/me/.ssh", "/Users/me/.aws"]
    }
  }
}
```

### Как это работает

- Команды Bash выполняются в песочнице с ограниченным доступом к файловой системе
- Сетевой доступ можно изолировать, чтобы не было непреднамеренных внешних соединений
- Работает вместе с правилами разрешений для защиты в глубину
- На macOS Seatbelt блокирует все сетевые соединения, кроме соединения с прокси песочницы; `sandbox.enableWeakerNetworkIsolation` **ослабляет** эту изоляцию и нужен только инструментам вроде CLI на Go за прокси MITM `httpProxyPort`

### Сценарии использования

- Безопасный запуск недоверенного или сгенерированного кода
- Защита от случайных изменений файлов вне проекта
- Ограничение сетевого доступа во время автоматизированных задач

## Управляемые настройки (Enterprise)

Управляемые настройки позволяют корпоративным администраторам разворачивать конфигурацию Claude Code по организации средствами управления, родными для платформы.

### Способы деплоя

| Платформа | Способ | С версии |
|-----------|--------|----------|
| macOS | Управляемые файлы plist (MDM) | v2.1.51+ |
| Windows | Реестр Windows | v2.1.51+ |
| Кроссплатформенно | Управляемые файлы конфигурации | v2.1.51+ |
| Кроссплатформенно | Управляемые drop-in (каталог `managed-settings.d/`) | v2.1.83+ |

### Управляемые drop-in

С v2.1.83 администраторы могут разложить несколько файлов управляемых настроек в каталог `managed-settings.d/`. Файлы сливаются в алфавитном порядке, поэтому конфигурацию можно собирать по частям для разных команд. Каталог лежит рядом с `managed-settings.json` в системном каталоге (`/Library/Application Support/ClaudeCode/` на macOS, `/etc/claude-code/` на Linux, `C:\Program Files\ClaudeCode\` на Windows):

```
/etc/claude-code/managed-settings.d/
  00-org-defaults.json
  10-team-policies.json
  20-project-overrides.json
```

### Доступные управляемые настройки

| Настройка | Описание |
|-----------|----------|
| `permissions.disableBypassPermissionsMode` | Задайте `"disable"`, чтобы пользователи не могли включать обход разрешений |
| `availableModels` | Ограничить, какие модели пользователи могут выбирать |
| `enforceAvailableModels` | (v2.1.175) Когда `true`, список допуска `availableModels` *также* ограничивает модель **Default** — если настроенная модель по умолчанию не в списке, Claude Code откатывается к первой разрешённой модели. Пользовательские и проектные настройки больше не могут расширить управляемый список `availableModels`. |
| `allowedChannelPlugins` | Какие плагины каналов разрешены |
| `autoMode.environment` | Доверенная инфраструктура для режима Auto |

## Конфигурация и настройки

### Расположение файлов конфигурации

1. **Пользовательские настройки**: `~/.claude/settings.json`
2. **Настройки проекта**: `.claude/settings.json` (в системе контроля версий)
3. **Локальные настройки проекта**: `.claude/settings.local.json` (не в системе контроля версий)
4. **Управляемые настройки**: `managed-settings.json` в системном каталоге (см. [Управляемые настройки](#управляемые-настройки-enterprise))

### Полный пример конфигурации

**Конфигурация основных продвинутых функций** (`.claude/settings.json`):

```json
{
  "permissions": {
    "defaultMode": "manual"
  },
  "hooks": {
    "PreToolUse": [
      { "matcher": "Edit", "hooks": [{ "type": "command", "command": "~/.claude/hooks/eslint-fix.sh" }] }
    ],
    "PostToolUse": [
      { "matcher": "Write", "hooks": [{ "type": "command", "command": "~/.claude/hooks/security-scan.sh" }] }
    ]
  }
}
```

Скрипты хуков получают вход инструмента как JSON на stdin (например, `tool_input.file_path`); подстановки `${file_path}` нет. MCP-серверы не являются ключом настроек — задавайте их в `.mcp.json` в корне проекта:

```json
{
  "mcpServers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/",
      "headers": { "Authorization": "Bearer ${GITHUB_PERSONAL_ACCESS_TOKEN}" }
    }
  }
}
```

**Расширенный пример конфигурации:**

```json
{
  "permissions": {
    "defaultMode": "manual",
    "allow": ["Bash(git log:*)", "Read"],
    "deny": ["Bash(rm -rf:*)"]
  },

  "hooks": {
    "PreToolUse": [{ "matcher": "Edit", "hooks": [{ "type": "command", "command": "~/.claude/hooks/eslint-fix.sh" }] }],
    "PostToolUse": [{ "matcher": "Write", "hooks": [{ "type": "command", "command": "~/.claude/hooks/security-scan.sh" }] }],
    "Stop": [{ "hooks": [{ "type": "command", "command": "~/.claude/hooks/notify.sh" }] }]
  }
}
```

MCP-сервер GitHub для этой схемы кладётся в `.mcp.json`, как показано выше.

### Запасные модели (`fallbackModel`)

Настройка `fallbackModel` позволяет задать **до трёх** запасных моделей, которые пробуются по порядку, когда основная модель перегружена или недоступна.

```json
{
  "fallbackModel": ["claude-opus-4-8", "claude-sonnet-4-6", "claude-haiku-4-5"]
}
```

С **v2.1.166** флаг `--fallback-model` действует и на интерактивные сессии (не только headless). При переключении Claude Code один раз повторяет неожиданную ошибку, которую обычно не повторяют; ошибки аутентификации, лимита запросов, размера запроса и транспорта по-прежнему падают сразу.

### Команды управления конфигурацией

```
Пользователь: /config
[Открывает интерактивное меню конфигурации]
```

Команда `/config` даёт интерактивное меню для переключения настроек, таких как:
- Расширенное мышление вкл/выкл
- Подробный вывод
- Режим разрешений
- Выбор модели
- Размер динамического workflow (v2.1.219) — скрыт, когда `workflowSizeGuideline` задан в файле настроек, см. [Динамические Workflows](#динамические-workflows)
- Сжатие при простое (v2.1.302)

В интерактивном меню Enter или Space меняют выбранную настройку, а Esc сохраняет и закрывает (v2.1.183+).

Настройку можно задать прямо из промпта, не открывая меню:

```bash
/config thinking=false      # задать одну настройку в строке (v2.1.181+)
/config --help              # перечислить доступные короткие ключи (v2.1.183+)
```

Сокращение `key=value` работает в интерактивных сессиях, с `-p` и в Remote Control.

### Конфигурация проекта

Создайте `.claude/settings.json` в проекте:

```json
{
  "hooks": {
    "PreToolUse": [{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "npm test && npm run lint" }] }]
  },
  "permissions": {
    "defaultMode": "manual"
  }
}
```

MCP-серверы проекта кладутся в `.mcp.json` в корне проекта:

```json
{
  "mcpServers": {
    "project-db": {
      "command": "mcp-postgres",
      "env": {
        "DATABASE_URL": "${PROJECT_DB_URL}"
      }
    }
  }
}
```

## Доверие и область разрешений

> **По данным журнала изменений (v2.1.222, v2.1.232)**: эти ужесточения взяты из журнала
> изменений; справочник настроек их пока не расписывает.

Повторяющаяся тема последних релизов: настройки, важные для безопасности, больше нельзя расширить
репозиторием, который вы клонировали. Три изменения, о которых стоит знать.

**Вложенным репозиториям нужно собственное подтверждение доверия (v2.1.232).** Git-репозиторий
внутри доверенного родительского каталога больше не наследует это доверие. Если вы доверяете
`~/work/monorepo`, а внутри лежит vendored-подмодуль, вас попросят отдельно доверять
подмодулю в первый раз, когда Claude Code будет работать внутри него.

**`sandbox.ripgrep` только в области пользователя (v2.1.232).** Настройка, которая называет двоичный файл ripgrep,
которым пользуется песочница, учитывается только из пользовательских настроек, управляемых настроек или
`--settings`. Настройки проекта больше не могут указать песочнице другой двоичный файл.

**Автозапуск Remote Control только в области пользователя (v2.1.222).** Локальные настройки репозитория не могут
включить автозапуск Remote Control; его можно включить только в области пользователя через `/config`.

Правило, которое стоит усвоить: если настройка позволила бы файлу из репозитория расширить то, что Claude
Code может делать на вашей машине, считайте, что теперь она только в области пользователя.

## Команды агентов

Agent Teams — экспериментальная функция, которая позволяет нескольким экземплярам Claude Code совместно работать над задачей. По умолчанию она выключена.

### Включение команд агентов

Включается переменной окружения или настройками:

```bash
# Переменная окружения
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
```

Или добавьте в JSON настроек:

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

### Как работают команды агентов

- **Ведущий команды** координирует общую задачу и поручает подзадачи участникам
- **Участники** работают независимо, у каждого своё контекстное окно
- **Общий список задач** позволяет участникам координироваться самим
- Определения субагентов (`.claude/agents/` или флаг `--agents`) задают роли и специализации участников

### Режимы отображения

Команды агентов поддерживают два режима отображения, которые задаются флагом `--teammate-mode`:

| Режим | Описание |
|-------|----------|
| `in-process` (по умолчанию) | Участники работают в том же процессе терминала |
| `tmux` | У каждого участника своя разделённая панель (нужны tmux или iTerm2) |
| `auto` | Автоматически выбирает лучший режим отображения |

```bash
# Разделённые панели tmux для показа участников
claude --teammate-mode tmux

# Явно использовать режим внутри процесса
claude --teammate-mode in-process
```

### Сценарии использования

- Крупный рефакторинг, где разные участники ведут разные модули
- Параллельные код-ревью и реализация
- Согласованные изменения многих файлов по кодовой базе

> **Примечание**: Agent Teams экспериментальны и могут измениться в будущих релизах. Полный справочник — [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams).

## Лучшие практики

### Режим планирования
- ✅ Используйте для сложных многошаговых задач
- ✅ Проверяйте планы перед одобрением
- ✅ Меняйте планы, когда это нужно
- ❌ Не используйте для простых задач

### Расширенное мышление
- ✅ Используйте для архитектурных решений
- ✅ Используйте для сложного решения задач
- ✅ Просматривайте ход рассуждения
- ❌ Не используйте для простых запросов

### Фоновые задачи
- ✅ Используйте для долгих операций
- ✅ Следите за прогрессом задач
- ✅ Аккуратно обрабатывайте сбои задач
- ❌ Не запускайте слишком много задач одновременно

### Разрешения
- ✅ Используйте `plan` для код-ревью (только чтение)
- ✅ Используйте `default` для интерактивной разработки
- ✅ Используйте `acceptEdits` для рабочих процессов автоматизации
- ✅ Используйте `auto` для автономной работы со страховочными ограничениями
- ❌ Не используйте `bypassPermissions`, если без этого действительно нельзя обойтись

### Сессии
- ✅ Используйте отдельные сессии для разных задач
- ✅ Сохраняйте важные состояния сессий
- ✅ Убирайте старые сессии
- ❌ Не смешивайте несвязанную работу в одной сессии
