# Закоммитить и отправить всё

⚠️ **ОСТОРОЖНО**: добавьте в индекс ВСЕ изменения, создайте коммит и отправьте на удалённый репозиторий. Используйте только когда уверены, что все изменения относятся к одному целому.

## Рабочий процесс

### 1. Анализ изменений
Запустите параллельно:
- `git status` — показать изменённые, добавленные, удалённые и неотслеживаемые файлы
- `git diff --stat` — показать статистику изменений
- `git log -1 --oneline` — показать последний коммит как образец стиля сообщения

### 2. Проверки безопасности

**❌ ОСТАНОВИТЕСЬ и ПРЕДУПРЕДИТЕ, если обнаружено:**
- Секреты: `.env*`, `*.key`, `*.pem`, `credentials.json`, `secrets.yaml`, `id_rsa`, `*.p12`, `*.pfx`, `*.cer`
- API-ключи: любые переменные `*_API_KEY`, `*_SECRET`, `*_TOKEN` с настоящими значениями (не заглушки вроде `your-api-key`, `xxx`, `placeholder`)
- Большие файлы: `>10MB` без Git LFS
- Артефакты сборки: `node_modules/`, `dist/`, `build/`, `__pycache__/`, `*.pyc`, `.venv/`
- Временные файлы: `.DS_Store`, `thumbs.db`, `*.swp`, `*.tmp`

**Проверка API-ключей:**
Проверьте изменённые файлы на шаблоны вроде:
```bash
OPENAI_API_KEY=sk-proj-xxxxx  # ❌ Обнаружен настоящий ключ!
AWS_SECRET_KEY=AKIA...         # ❌ Обнаружен настоящий ключ!
STRIPE_API_KEY=sk_live_...    # ❌ Обнаружен настоящий ключ!

# ✅ Допустимые заглушки:
API_KEY=your-api-key-here
SECRET_KEY=placeholder
TOKEN=xxx
API_KEY=<your-key>
SECRET=${YOUR_SECRET}
```

**✅ Проверьте:**
- `.gitignore` настроен правильно
- Нет конфликтов слияния
- Верная ветка (предупредите, если это main/master)
- API-ключи — только заглушки

### 3. Запрос подтверждения

Покажите сводку:
```
📊 Сводка изменений:
- X файлов изменено, Y добавлено, Z удалено
- Итого: +AAA вставок, -BBB удалений

🔒 Безопасность: ✅ Нет секретов | ✅ Нет больших файлов | ⚠️ [предупреждения]
🌿 Ветка: [имя] → origin/[имя]

Я сделаю: git add . → commit → push

Введите 'yes', чтобы продолжить, или 'no', чтобы отменить.
```

**ЖДИТЕ явного "yes", прежде чем продолжать.**

### 4. Выполнение (после подтверждения)

Запустите последовательно:
```bash
git add .
git status  # Проверьте индекс
```

### 5. Сообщение коммита

Проанализируйте изменения и составьте сообщение в формате conventional commits:

**Формат:**
```
[type]: Краткая сводка (не более 72 символов)

- Ключевое изменение 1
- Ключевое изменение 2
- Ключевое изменение 3
```

**Типы:** `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `perf`, `build`, `ci`

**Пример:**
```
docs: Обновить README концепций подробной документацией

- Добавить диаграммы архитектуры и таблицы
- Включить практические примеры
- Расширить разделы о лучших практиках
```

### 6. Коммит и отправка

```bash
git commit -m "$(cat <<'EOF'
[Сгенерированное сообщение коммита]
EOF
)"
git push  # Если не удалось: git pull --rebase && git push
git log -1 --oneline --decorate  # Проверьте
```

### 7. Подтверждение успеха

```
✅ Успешно отправлено на удалённый репозиторий!

Коммит: [хеш] [сообщение]
Ветка: [ветка] → origin/[ветка]
Изменённые файлы: X (+вставок, -удалений)
```

## Обработка ошибок

- **git add не удался**: проверьте разрешения, заблокированные файлы, что репозиторий инициализирован
- **git commit не удался**: исправьте хуки pre-commit, проверьте git config (user.name/email)
- **git push не удался**:
  - Не fast-forward: `git pull --rebase && git push`
  - Нет удалённой ветки: `git push -u origin [branch]`
  - Защищённая ветка: вместо этого используйте рабочий процесс PR

## Когда использовать

✅ **Хорошо:**
- Обновление документации в нескольких файлах
- Функция вместе с тестами и документацией
- Исправления ошибок в нескольких файлах
- Форматирование или рефакторинг по всему проекту
- Изменения конфигурации

❌ **Избегайте:**
- Неясно, что попадёт в коммит
- Есть секреты или конфиденциальные данные
- Защищённые ветки без ревью
- Есть конфликты слияния
- Нужна дробная история коммитов
- Хуки pre-commit падают

## Альтернативы

Если пользователю нужен контроль, предложите:
1. **Выборочная индексация**: просмотреть и добавить в индекс конкретные файлы
2. **Интерактивная индексация**: `git add -p` для выбора кусков
3. **Рабочий процесс PR**: создать ветку → отправить → PR (команда `/pr`)

**⚠️ Помните**: всегда просматривайте изменения перед отправкой. Если сомневаетесь, отдельные команды git дают больше контроля.
