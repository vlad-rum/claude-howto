# Каталог запахов кода

Подробный справочник запахов кода по книге Мартина Фаулера (Martin Fowler) *Refactoring* («Рефакторинг», 2-е издание). Запахи кода — это симптомы более глубоких проблем: они показывают, что с проектированием кода, возможно, что-то не так.

> «Запах кода — это поверхностный признак, который обычно соответствует более глубокой проблеме в системе.» — Martin Fowler

---

## Раздувальщики

Запахи кода, которые означают, что нечто выросло слишком большим, чтобы с ним эффективно работать.

### Длинный метод

**Признаки:**
- Метод длиннее 30–50 строк
- Нужно прокручивать, чтобы увидеть метод целиком
- Несколько уровней вложенности
- Комментарии объясняют, что делают участки

**Почему это плохо:**
- Трудно понять
- Трудно тестировать изолированно
- Изменения дают непредвиденные последствия
- Внутри прячется дублирующаяся логика

**Рефакторинги:**
- Извлечение метода (Extract Method)
- Замена временной переменной вызовом метода (Replace Temp with Query)
- Введение объекта-параметра (Introduce Parameter Object)
- Замена метода объектом методов (Replace Method with Method Object)
- Декомпозиция условного оператора (Decompose Conditional)

**Пример (до):**
```javascript
function processOrder(order) {
  // Проверить заказ (20 строк)
  if (!order.items) throw new Error('No items');
  if (order.items.length === 0) throw new Error('Empty order');
  // ... ещё проверки

  // Посчитать итоги (30 строк)
  let subtotal = 0;
  for (const item of order.items) {
    subtotal += item.price * item.quantity;
  }
  // ... налог, доставка, скидки

  // Отправить уведомления (20 строк)
  // ... логика электронной почты
}
```

**Пример (после):**
```javascript
function processOrder(order) {
  validateOrder(order);
  const totals = calculateOrderTotals(order);
  sendOrderNotifications(order, totals);
  return { order, totals };
}
```

### Большой класс

**Признаки:**
- У класса много переменных экземпляра (>7–10)
- У класса много методов (>15–20)
- Имя класса расплывчатое (Manager, Handler, Processor)
- Методы не используют все переменные экземпляра

**Почему это плохо:**
- Нарушает принцип единственной ответственности (Single Responsibility Principle)
- Трудно тестировать
- Изменения расходятся по несвязанным функциям
- Трудно переиспользовать части

**Рефакторинги:**
- Извлечение класса (Extract Class)
- Извлечение подкласса (Extract Subclass)
- Извлечение интерфейса (Extract Interface)

**Обнаружение:**
```
Строк кода > 300
Число методов > 15
Число полей > 10
```

---

### Одержимость элементарными типами

**Признаки:**
- Примитивы для понятий предметной области (string для электронной почты, int для денег)
- Массивы примитивов вместо объектов
- Строковые константы для кодов типа
- Магические числа и строки

**Почему это плохо:**
- Нет проверки на уровне типа
- Логика размазана по кодовой базе
- Легко передать неверные значения
- Потеряны понятия предметной области

**Рефакторинги:**
- Замена простого значения объектом (Replace Primitive with Object)
- Замена кода типа классом (Replace Type Code with Class)
- Замена кода типа подклассами (Replace Type Code with Subclasses)
- Замена кода типа состоянием/стратегией (Replace Type Code with State/Strategy)

**Пример (до):**
```javascript
const user = {
  email: 'john@example.com',     // Просто строка
  phone: '1234567890',           // Просто строка
  status: 'active',              // Магическая строка
  balance: 10050                 // Центы как целое число
};
```

**Пример (после):**
```javascript
const user = {
  email: new Email('john@example.com'),
  phone: new PhoneNumber('1234567890'),
  status: UserStatus.ACTIVE,
  balance: Money.cents(10050)
};
```

### Длинный список параметров

**Признаки:**
- Методы с 4+ параметрами
- Параметры, которые всегда встречаются вместе
- Логические флаги, меняющие поведение метода
- Часто передаётся null/undefined

**Почему это плохо:**
- Трудно вызвать правильно
- Путаница в порядке параметров
- Признак того, что метод делает слишком много
- Трудно добавлять новые параметры

**Рефакторинги:**
- Введение объекта-параметра (Introduce Parameter Object)
- Сохранение всего объекта (Preserve Whole Object)
- Замена параметра вызовом метода (Replace Parameter with Method Call)
- Удаление аргумента-флага (Remove Flag Argument)

**Пример (до):**
```javascript
function createUser(firstName, lastName, email, phone,
                    street, city, state, zip,
                    isAdmin, isActive, createdBy) {
  // ...
}
```

**Пример (после):**
```javascript
function createUser(personalInfo, address, options) {
  // personalInfo: { firstName, lastName, email, phone }
  // address: { street, city, state, zip }
  // options: { isAdmin, isActive, createdBy }
}
```

---

### Группы данных

**Признаки:**
- Одни и те же 3+ поля многократно встречаются вместе
- Параметры, которые всегда путешествуют вместе
- Классы, у которых подмножества полей принадлежат друг другу

**Почему это плохо:**
- Дублируется логика обработки
- Не хватает абстракции
- Труднее расширять
- Указывает на скрытый класс

**Рефакторинги:**
- Извлечение класса (Extract Class)
- Введение объекта-параметра (Introduce Parameter Object)
- Сохранение всего объекта (Preserve Whole Object)

**Пример:**
```javascript
// Группа данных: координаты (x, y, z)
function movePoint(x, y, z, dx, dy, dz) { }
function scalePoint(x, y, z, factor) { }
function distanceBetween(x1, y1, z1, x2, y2, z2) { }

// Извлечь класс Point3D
class Point3D {
  constructor(x, y, z) { }
  move(delta) { }
  scale(factor) { }
  distanceTo(other) { }
}
```

## Нарушители объектной ориентации

Запахи, которые указывают на неполное или неверное применение принципов ООП (объектно-ориентированного программирования).

### Операторы switch

**Признаки:**
- Длинные цепочки switch/case или if/else
- Один и тот же switch в нескольких местах
- Switch по кодам типа
- Добавление новых веток требует правок повсюду

**Почему это плохо:**
- Нарушает принцип открытости/закрытости (Open/Closed Principle)
- Изменения расходятся по всем местам со switch
- Трудно расширять
- Часто указывает на отсутствие полиморфизма

**Рефакторинги:**
- Замена условного оператора полиморфизмом (Replace Conditional with Polymorphism)
- Замена кода типа подклассами (Replace Type Code with Subclasses)
- Замена кода типа состоянием/стратегией (Replace Type Code with State/Strategy)

**Пример (до):**
```javascript
function calculatePay(employee) {
  switch (employee.type) {
    case 'hourly':
      return employee.hours * employee.rate;
    case 'salaried':
      return employee.salary / 12;
    case 'commissioned':
      return employee.sales * employee.commission;
  }
}
```

**Пример (после):**
```javascript
class HourlyEmployee {
  calculatePay() {
    return this.hours * this.rate;
  }
}

class SalariedEmployee {
  calculatePay() {
    return this.salary / 12;
  }
}
```

### Временное поле

**Признаки:**
- Переменные экземпляра используются лишь в некоторых методах
- Поля задаются условно
- Сложная инициализация для отдельных случаев

**Почему это плохо:**
- Путаница — поле есть, но может быть null
- Трудно понять состояние объекта
- Признак спрятанной условной логики

**Рефакторинги:**
- Извлечение класса (Extract Class)
- Введение объекта Null (Introduce Null Object)
- Замена временного поля локальной переменной (Replace Temp Field with Local)

---

### Отказ от наследства

**Признаки:**
- Подкласс не использует унаследованные методы и данные
- Подкласс переопределяет методы так, что они ничего не делают
- Наследование используется для переиспользования кода, а не для отношения «является» (IS-A)

**Почему это плохо:**
- Неверная абстракция
- Нарушает принцип подстановки Лисков (Liskov Substitution Principle)
- Иерархия вводит в заблуждение

**Рефакторинги:**
- Спуск метода/поля (Push Down Method/Field)
- Замена подкласса делегатом (Replace Subclass with Delegate)
- Замена наследования делегированием (Replace Inheritance with Delegation)

---

### Альтернативные классы с разными интерфейсами

**Признаки:**
- Два класса делают похожие вещи
- Разные имена методов для одного понятия
- Их можно было бы использовать взаимозаменяемо

**Почему это плохо:**
- Дублирующиеся реализации
- Нет общего интерфейса
- Трудно переключаться между ними

**Рефакторинги:**
- Переименование метода (Rename Method)
- Перемещение метода (Move Method)
- Извлечение суперкласса (Extract Superclass)
- Извлечение интерфейса (Extract Interface)

## Затруднители изменений

Запахи, из-за которых изменения даются трудно — чтобы изменить одно, приходится менять многое другое.

### Расходящиеся модификации

**Признаки:**
- Один класс меняют по нескольким разным причинам
- Изменения в разных областях приводят к правкам одного и того же класса
- Класс — «божественный класс» (God class)

**Почему это плохо:**
- Нарушает принцип единственной ответственности
- Высокая частота изменений
- Конфликты слияния

**Рефакторинги:**
- Извлечение класса (Extract Class)
- Извлечение суперкласса (Extract Superclass)
- Извлечение подкласса (Extract Subclass)

**Пример:**
Класс `User` меняется из-за:
- изменений аутентификации
- изменений профиля
- изменений биллинга
- изменений уведомлений

→ Извлечь: `AuthService`, `ProfileService`, `BillingService`, `NotificationService`

---

### Стрельба дробью

**Признаки:**
- Одно изменение требует правок во многих классах
- Небольшая функция требует затронуть 10+ файлов
- Изменения разбросаны, трудно найти все места

**Почему это плохо:**
- Легко пропустить место
- Высокая связанность
- Изменения подвержены ошибкам

**Рефакторинги:**
- Перемещение метода (Move Method)
- Перемещение поля (Move Field)
- Встраивание класса (Inline Class)

**Обнаружение:**
Ищите: добавление одного поля требует изменений более чем в 5 файлах.

---

### Параллельные иерархии наследования

**Признаки:**
- Создание подкласса в одной иерархии требует подкласса в другой
- Префиксы классов совпадают (например, `DatabaseOrder`, `DatabaseProduct`)

**Почему это плохо:**
- Двойной объём сопровождения
- Связанность между иерархиями
- Легко забыть одну сторону

**Рефакторинги:**
- Перемещение метода (Move Method)
- Перемещение поля (Move Field)
- Устранить одну из иерархий

## Замусориватели

Нечто лишнее, что следует удалить.

### Комментарии (избыточные)

**Признаки:**
- Комментарии объясняют, что делает код
- Закомментированный код
- TODO/FIXME, которые висят вечно
- Извинения в комментариях

**Почему это плохо:**
- Комментарии врут (расходятся с кодом)
- Код должен быть самодокументируемым
- Мёртвый код вызывает путаницу

**Рефакторинги:**
- Извлечение метода (Extract Method) — имя объясняет, что делается
- Переименование (Rename) — ясность без комментариев
- Удалить закомментированный код
- Введение утверждения (Introduce Assertion)

**Хорошие и плохие комментарии:**
```javascript
// ПЛОХО: объясняет, что делается
// Цикл по пользователям и проверка, активны ли они
for (const user of users) {
  if (user.status === 'active') { }
}

// ХОРОШО: объясняет, почему
// Только активные пользователи — неактивных обрабатывает задание очистки
const activeUsers = users.filter(u => u.isActive);
```

---

### Дублирование кода

**Признаки:**
- Один и тот же код в нескольких местах
- Похожий код с небольшими отличиями
- Шаблоны копирования (copy-paste)

**Почему это плохо:**
- Исправления ошибок нужны в нескольких местах
- Риск рассогласования
- Раздутая кодовая база

**Рефакторинги:**
- Извлечение метода (Extract Method)
- Извлечение класса (Extract Class)
- Подъём метода (Pull Up Method) в иерархиях
- Формирование шаблонного метода (Form Template Method)

**Правило обнаружения:**
Любой код, дублирующийся 3+ раза, следует извлечь.

---

### Ленивый класс

**Признаки:**
- Класс делает недостаточно, чтобы оправдать своё существование
- Обёртка без добавленной пользы
- Результат переусложнения

**Почему это плохо:**
- Накладные расходы на сопровождение
- Лишняя косвенность
- Сложность без выгоды

**Рефакторинги:**
- Встраивание класса (Inline Class)
- Свёртывание иерархии (Collapse Hierarchy)

---

### Мёртвый код

**Признаки:**
- Недостижимый код
- Неиспользуемые переменные, методы, классы
- Закомментированный код
- Код за невозможными условиями

**Почему это плохо:**
- Путаница
- Бремя сопровождения
- Замедляет понимание

**Рефакторинги:**
- Удаление мёртвого кода (Remove Dead Code)
- Безопасное удаление (Safe Delete)

**Обнаружение:**
```bash
# Ищите неиспользуемые экспорты
# Ищите функции без ссылок
# Предупреждения IDE о «неиспользуемом»
```

---

### Теоретическая общность

**Признаки:**
- Абстрактные классы с одним подклассом
- Неиспользуемые параметры «на будущее»
- Методы, которые только делегируют
- «Фреймворк» для одного сценария использования

**Почему это плохо:**
- Сложность без выгоды
- YAGNI (You Ain't Gonna Need It, «вам это не понадобится»)
- Труднее понять

**Рефакторинги:**
- Свёртывание иерархии (Collapse Hierarchy)
- Встраивание класса (Inline Class)
- Удаление параметра (Remove Parameter)
- Переименование метода (Rename Method)

## Опутыватели связями

Запахи, которые означают чрезмерную связанность между классами.

### Зависть к функциям

**Признаки:**
- Метод больше использует данные другого класса, чем свои
- Много вызовов геттеров другого объекта
- Данные и поведение разделены

**Почему это плохо:**
- Поведение лежит не там
- Слабая инкапсуляция
- Трудно сопровождать

**Рефакторинги:**
- Перемещение метода (Move Method)
- Перемещение поля (Move Field)
- Извлечение метода (Extract Method), затем перемещение

**Пример (до):**
```javascript
class Order {
  getDiscountedPrice(customer) {
    // Активно использует данные customer
    if (customer.loyaltyYears > 5) {
      return this.price * customer.discountRate;
    }
    return this.price;
  }
}
```

**Пример (после):**
```javascript
class Customer {
  getDiscountedPriceFor(price) {
    if (this.loyaltyYears > 5) {
      return price * this.discountRate;
    }
    return price;
  }
}
```

---

### Неуместная близость

**Признаки:**
- Классы обращаются к закрытым частям друг друга
- Двунаправленные ссылки
- Подклассы слишком много знают о родителях

**Почему это плохо:**
- Высокая связанность
- Изменения идут каскадом
- Трудно изменить одно без другого

**Рефакторинги:**
- Перемещение метода (Move Method)
- Перемещение поля (Move Field)
- Замена двунаправленной связи однонаправленной (Change Bidirectional to Unidirectional)
- Извлечение класса (Extract Class)
- Сокрытие делегата (Hide Delegate)

---

### Цепочки сообщений

**Признаки:**
- Длинные цепочки вызовов методов: `a.getB().getC().getD().getValue()`
- Клиент зависит от структуры навигации
- Код в стиле «крушение поезда» (train wreck)

**Почему это плохо:**
- Хрупкость — любое изменение рвёт цепочку
- Нарушает закон Деметры (Law of Demeter)
- Связанность со структурой

**Рефакторинги:**
- Сокрытие делегата (Hide Delegate)
- Извлечение метода (Extract Method)
- Перемещение метода (Move Method)

**Пример:**
```javascript
// Плохо: цепочка сообщений
const managerName = employee.getDepartment().getManager().getName();

// Лучше: сокрытие делегирования
const managerName = employee.getManagerName();
```

---

### Посредник

**Признаки:**
- Класс, который только делегирует другому
- Половина методов — делегирование
- Нет добавленной пользы

**Почему это плохо:**
- Лишняя косвенность
- Накладные расходы на сопровождение
- Запутанная архитектура

**Рефакторинги:**
- Удаление посредника (Remove Middle Man)
- Встраивание метода (Inline Method)

---

## Шкала серьёзности запахов

| Серьёзность | Описание | Действие |
|-------------|----------|----------|
| **Критическая** | Блокирует разработку, вызывает ошибки | Исправить немедленно |
| **Высокая** | Существенное бремя сопровождения | Исправить в текущем спринте |
| **Средняя** | Заметно, но терпимо | Запланировать на ближайшее время |
| **Низкая** | Мелкое неудобство | Исправлять по случаю |

## Краткий чеклист обнаружения

Используйте этот чеклист при просмотре кода:

- [ ] Есть метод длиннее 30 строк?
- [ ] Есть класс длиннее 300 строк?
- [ ] Есть метод с более чем 4 параметрами?
- [ ] Есть дублирующиеся блоки кода?
- [ ] Есть switch/case по кодам типа?
- [ ] Есть неиспользуемый код?
