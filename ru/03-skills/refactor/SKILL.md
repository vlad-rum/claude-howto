# Навык рефакторинга кода

Систематический подход к рефакторингу кода по книге Мартина Фаулера (Martin Fowler) *Refactoring: Improving the Design of Existing Code* («Рефакторинг. Улучшение проекта существующего кода», 2-е издание). Этот навык делает упор на безопасные пошаговые изменения, подкреплённые тестами.

> «Рефакторинг — это процесс такого изменения программной системы, при котором внешнее поведение кода не меняется, а внутренняя структура улучшается.» — Martin Fowler

## Основные принципы

1. **Сохранение поведения**: внешнее поведение должно остаться неизменным
2. **Малые шаги**: делайте крошечные проверяемые изменения
3. **Опора на тесты**: тесты — это страховочная сеть
4. **Непрерывность**: рефакторинг идёт постоянно, это не разовое событие
5. **Совместная работа**: на каждой фазе нужно одобрение пользователя

## Обзор рабочего процесса

```
Фаза 1: Исследование и анализ
    ↓
Фаза 2: Оценка покрытия тестами
    ↓
Фаза 3: Выявление запахов кода
    ↓
Фаза 4: Создание плана рефакторинга
    ↓
Фаза 5: Пошаговая реализация
    ↓
Фаза 6: Обзор и итерация
```

## Фаза 1: Исследование и анализ

### Цели
- Понять структуру кодовой базы и её назначение
- Определить область рефакторинга
- Собрать контекст о бизнес-требованиях

### Вопросы пользователю
Прежде чем начать, уточните:

1. **Область**: какие файлы, модули или функции нужно отрефакторить?
2. **Цели**: какие проблемы вы пытаетесь решить? (читаемость, производительность, сопровождаемость)
3. **Ограничения**: есть ли области, которые НЕ следует менять?
4. **Сроки**: это блокирует другую работу?
5. **Состояние тестов**: тесты есть? Они проходят?

### Действия
- [ ] Прочитать и понять целевой код
- [ ] Выявить зависимости и интеграции
- [ ] Задокументировать текущую архитектуру
- [ ] Отметить существующие маркеры технического долга (TODO, FIXME)

### Результат
Представьте выводы пользователю:
- Сводка структуры кода
- Выявленные проблемные места
- Первые рекомендации
- **Запросите одобрение, чтобы продолжить**

## Фаза 2: Оценка покрытия тестами

### Почему тесты важны
> «Рефакторинг без тестов — как езда без ремня безопасности.» — Martin Fowler

Тесты — **главная опора** безопасного рефакторинга. Без них вы рискуете внести ошибки.

### Шаги оценки

1. **Проверьте, есть ли тесты**
   ```bash
   # Ищите тестовые файлы
   find . -name "*test*" -o -name "*spec*" | head -20
   ```

2. **Запустите существующие тесты**
   ```bash
   # JavaScript/TypeScript
   npm test

   # Python
   pytest -v

   # Java
   mvn test
   ```

3. **Проверьте покрытие (если оно доступно)**
   ```bash
   # JavaScript
   npm run test:coverage

   # Python
   pytest --cov=.
   ```

### Точка решения: спросить пользователя

**Если тесты есть и проходят:**
- Переходите к фазе 3

**Если тестов нет или они неполные:**
Предложите варианты:
1. Сначала написать тесты (рекомендуется)
2. Добавлять тесты по ходу рефакторинга
3. Продолжить без тестов (рискованно — нужно явное согласие пользователя)

**Если тесты падают:**
- СТОП. Исправьте падающие тесты до рефакторинга
- Спросите пользователя: сначала исправить тесты?

### Рекомендации по написанию тестов (если нужно)

Для каждой рефакторируемой функции убедитесь, что тесты покрывают:
- Основной сценарий (штатная работа)
- Граничные случаи (пустой ввод, null, границы)
- Сценарии ошибок (недопустимый ввод, исключения)

Используйте цикл «красный — зелёный — рефакторинг» (red-green-refactor):
1. Напишите падающий тест (красный)
2. Добейтесь его прохождения (зелёный)
3. Выполните рефакторинг

## Фаза 3: Выявление запахов кода

### Что такое запахи кода?
Симптомы более глубоких проблем в коде. Это не ошибки, а признаки того, что код можно улучшить.

### Какие запахи кода проверять

Полный каталог — в [references/code-smells.md](references/code-smells.md).

#### Краткий справочник

| Запах | Признаки | Влияние |
|-------|----------|---------|
| **Длинный метод** | Методы длиннее 30–50 строк | Трудно понять, тестировать и сопровождать |
| **Дублирование кода** | Одна и та же логика в нескольких местах | Исправления ошибок нужны в нескольких местах |
| **Большой класс** | Класс со слишком многими ответственностями | Нарушает принцип единственной ответственности |
| **Зависть к функциям** | Метод больше использует данные другого класса | Слабая инкапсуляция |
| **Одержимость элементарными типами** | Злоупотребление примитивами вместо объектов | Потеряны понятия предметной области |
| **Длинный список параметров** | Методы с 4+ параметрами | Трудно вызвать правильно |
| **Группы данных** | Одни и те же элементы данных встречаются вместе | Не хватает абстракции |
| **Операторы switch** | Сложные цепочки switch/if-else | Трудно расширять |
| **Теоретическая общность** | Код «на всякий случай» | Лишняя сложность |
| **Мёртвый код** | Неиспользуемый код | Путаница, бремя сопровождения |

### Шаги анализа

1. **Автоматический анализ** (если скрипты доступны)
   ```bash
   python scripts/detect-smells.py <file>
   ```

2. **Ручной обзор**
   - Пройдите код систематически
   - Отметьте каждый запах с местом и серьёзностью
   - Разделите по влиянию (критический / высокий / средний / низкий)

3. **Приоритизация**
   Сосредоточьтесь на запахах, которые:
   - блокируют текущую разработку
   - вызывают ошибки или путаницу
   - затрагивают самые изменяемые пути в коде

### Результат: отчёт о запахах

Представьте пользователю:
- Список выявленных запахов с местами
- Оценку серьёзности каждого
- Рекомендуемый порядок приоритетов
- **Запросите одобрение приоритетов**

## Фаза 4: Создание плана рефакторинга

### Выбор рефакторингов

Для каждого запаха выберите подходящий рефакторинг из каталога.

Полный список — в [references/refactoring-catalog.md](references/refactoring-catalog.md).

#### Соответствие запахов и рефакторингов

| Запах кода | Рекомендуемые рефакторинги |
|------------|----------------------------|
| Длинный метод | Извлечение метода (Extract Method), замена временной переменной вызовом метода (Replace Temp with Query) |
| Дублирование кода | Извлечение метода (Extract Method), подъём метода (Pull Up Method), формирование шаблонного метода (Form Template Method) |
| Большой класс | Извлечение класса (Extract Class), извлечение подкласса (Extract Subclass) |
| Зависть к функциям | Перемещение метода (Move Method), перемещение поля (Move Field) |
| Одержимость элементарными типами | Замена простого значения объектом (Replace Primitive with Object), замена кода типа классом (Replace Type Code with Class) |
| Длинный список параметров | Введение объекта-параметра (Introduce Parameter Object), сохранение всего объекта (Preserve Whole Object) |
| Группы данных | Извлечение класса (Extract Class), введение объекта-параметра (Introduce Parameter Object) |
| Операторы switch | Замена условного оператора полиморфизмом (Replace Conditional with Polymorphism) |
| Теоретическая общность | Свёртывание иерархии (Collapse Hierarchy), встраивание класса (Inline Class), удаление мёртвого кода (Remove Dead Code) |
| Мёртвый код | Удаление мёртвого кода (Remove Dead Code) |

### Структура плана

Используйте шаблон [templates/refactoring-plan.md](templates/refactoring-plan.md).

Для каждого рефакторинга:
1. **Цель**: какой код изменится
2. **Запах**: какую проблему это решает
3. **Рефакторинг**: какой приём применить
4. **Шаги**: подробные микрошаги
5. **Риски**: что может пойти не так
6. **Откат**: как отменить, если понадобится

### Поэтапный подход

**КРИТИЧНО**: вводите рефакторинг постепенно, по фазам.

**Фаза A: Быстрые победы** (низкий риск, высокая ценность)
- Переименовать переменные для ясности
- Извлечь очевидный дублирующийся код
- Удалить мёртвый код

**Фаза B: Структурные улучшения** (средний риск)
- Извлечь методы из длинных функций
- Ввести объекты-параметры
- Переместить методы в подходящие классы

**Фаза C: Архитектурные изменения** (более высокий риск)
- Заменить условные операторы полиморфизмом
- Извлечь классы
- Ввести паттерны проектирования

### Точка решения: представить план пользователю

Перед реализацией:
- Покажите полный план рефакторинга
- Объясните каждую фазу и её риски
- Получите явное одобрение каждой фазы
- **Спросите**: «Продолжить с фазой A?»

## Фаза 5: Пошаговая реализация

### Золотое правило
> «Изменение → Тест → Зелёный? → Коммит → Следующий шаг»

### Ритм реализации

Для каждого шага рефакторинга:

1. **Предварительная проверка**
   - Тесты проходят (зелёный)
   - Код компилируется

2. **Сделайте ОДНО небольшое изменение**
   - Следуйте механике из каталога
   - Держите изменения минимальными

3. **Проверка**
   - Сразу запустите тесты
   - Проверьте ошибки компиляции

4. **Если тесты проходят (зелёный)**
   - Сделайте коммит с понятным сообщением
   - Переходите к следующему шагу

5. **Если тесты падают (красный)**
   - Немедленно СТОП
   - Отмените изменение
   - Разберите, что пошло не так
   - Спросите пользователя, если неясно

### Стратегия коммитов

Каждый коммит должен быть:
- **Атомарным**: одно логическое изменение
- **Обратимым**: легко откатить
- **Понятным**: ясное сообщение коммита

Примеры сообщений коммитов:
```
refactor: Извлечь calculateTotal() из processOrder()
refactor: Переименовать «x» в «customerCount» для ясности
refactor: Удалить неиспользуемый метод validateOldFormat()
```

### Отчёт о прогрессе

После каждой подфазы сообщите пользователю:
- Какие изменения сделаны
- Тесты всё ещё проходят?
- Какие проблемы встретились
- **Спросите**: «Продолжить со следующей порцией?»

## Фаза 6: Обзор и итерация

### Чеклист после рефакторинга

- [ ] Все тесты проходят
- [ ] Нет новых предупреждений и ошибок
- [ ] Код успешно компилируется
- [ ] Поведение не изменилось (ручная проверка)
- [ ] Документация обновлена, если нужно
- [ ] История коммитов чистая

### Сравнение метрик

Запустите анализ сложности до и после:
```bash
python scripts/analyze-complexity.py <file>
```

Покажите улучшения:
- Изменение числа строк кода
- Изменение цикломатической сложности
- Изменение индекса сопровождаемости

### Обзор пользователя

Представьте итоговые результаты:
- Сводку всех изменений
- Сравнение кода до и после
- Улучшение метрик
- Оставшийся технический долг
- **Спросите**: «Вас устраивают эти изменения?»

### Дальнейшие шаги

Обсудите с пользователем:
- Есть ещё запахи, которые стоит разобрать?
- Запланировать следующий рефакторинг?
- Применить похожие изменения в других местах?

## Важные указания

### Когда ОСТАНОВИТЬСЯ и спросить

Всегда останавливайтесь и советуйтесь с пользователем, когда:
- Неясна бизнес-логика
- Изменение может затронуть внешние API (программные интерфейсы)
- Покрытие тестами недостаточно
- Нужно серьёзное архитектурное решение
- Уровень риска растёт
- возникла неожиданная сложность

### Правила безопасности

1. **Никогда не рефакторьте без тестов** (если только пользователь явно не принял риск)
2. **Никогда не делайте крупных изменений** — разбивайте на крошечные шаги
3. **Никогда не пропускайте запуск тестов** после каждого изменения
4. **Никогда не продолжайте, если тесты падают** — сначала исправьте или откатите
5. **Никогда не предполагайте** — если сомневаетесь, спросите

### Чего делать не нужно

- Не совмещайте рефакторинг с добавлением функций
- Не рефакторьте во время аварий в продакшене
- Не рефакторьте код, который не понимаете
- Не переусложняйте — сохраняйте простоту
- Не рефакторьте всё сразу

## Быстрый пример

### Сценарий: длинный метод с дублированием

**До:**
```javascript
function processOrder(order) {
  // 150 строк кода, среди них:
  // - дублирующаяся логика проверки
  // - встроенные вычисления
  // - смешанные ответственности
}
```

**Шаги рефакторинга:**

1. **Убедитесь, что тесты есть** для processOrder()
2. **Извлеките** проверку в validateOrder()
3. **Протестируйте** — должно пройти
4. **Извлеките** вычисление в calculateOrderTotal()
5. **Протестируйте** — должно пройти
6. **Извлеките** уведомление в notifyCustomer()
7. **Протестируйте** — должно пройти
8. **Проверьте** — processOrder() теперь оркестрирует 3 ясные функции

**После:**
```javascript
function processOrder(order) {
  validateOrder(order);
  const total = calculateOrderTotal(order);
  notifyCustomer(order, total);
  return { order, total };
}
```
