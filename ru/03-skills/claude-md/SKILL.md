## Ввод пользователя

```text
$ARGUMENTS
```

**Обязательно** учтите ввод пользователя, прежде чем продолжать (если он не пуст). Пользователь может указать:
- `create` — создать новый CLAUDE.md с нуля
- `update` — улучшить существующий CLAUDE.md
- `audit` — разобрать текущий CLAUDE.md и отчитаться о качестве
- Конкретный путь, где создать или обновить файл (например, `src/api/CLAUDE.md` для инструкций конкретного каталога)

## Основные принципы

**LLM не хранят состояние**: CLAUDE.md — главный файл проекта, который загружается в каждый разговор (рядом с автопамятью и правилами без области). Это основной документ онбординга ИИ-агентов в вашу кодовую базу.

### Золотые правила

1. **Меньше — значит лучше**: передовые LLM удерживают около 150–200 инструкций. Системный промпт Claude Code уже занимает около 50. Держите CLAUDE.md собранным и коротким.

2. **Применимость ко всем сессиям**: включайте только то, что нужно в КАЖДОЙ сессии. Инструкции под конкретную задачу уносите в отдельные файлы.

3. **Не используйте Claude как линтер**: правила стиля раздувают контекст и ухудшают следование инструкциям. Используйте детерминированные инструменты (prettier, eslint и другие).

4. **Никогда не генерируйте автоматически**: CLAUDE.md — точка наибольшего влияния в обвязке ИИ. Составляйте его вручную и обдуманно.

## Порядок выполнения

### 1. Анализ проекта

Сначала разберите текущее состояние проекта:

1. Проверьте, есть ли уже файлы CLAUDE.md:
   - В корне: `./CLAUDE.md` или `.claude/CLAUDE.md`
   - Для отдельных каталогов: `**/CLAUDE.md`
   - Глобальная пользовательская конфигурация: `~/.claude/CLAUDE.md`

2. Определите структуру проекта:
   - Технологический стек (языки, фреймворки)
   - Тип проекта (монорепозиторий, одно приложение, библиотека)
   - Инструменты разработки (менеджер пакетов, система сборки, раннер тестов)

3. Просмотрите существующую документацию:
   - README.md
   - CONTRIBUTING.md
   - package.json, pyproject.toml, Cargo.toml и другие

### 2. Стратегия содержания (ЧТО, ЗАЧЕМ, КАК)

Стройте CLAUDE.md вокруг трёх осей:

#### ЧТО — технологии и структура
- Обзор технологического стека
- Организация проекта (особенно важно для монорепозиториев)
- Ключевые каталоги и зачем они

#### ЗАЧЕМ — цель и контекст
- Что делает проект
- Почему приняты те или иные архитектурные решения
- За что отвечает каждый крупный компонент

#### КАК — рабочий процесс и соглашения
- Рабочий процесс разработки (bun или node, pip или uv и так далее)
- Процедуры и команды тестирования
- Способы проверки и сборки
- Критичные подводные камни и неочевидные требования

### 3. Стратегия постепенного раскрытия

Для крупных проектов рекомендуйте папку `agent_docs/`:

```
agent_docs/
  |- building_the_project.md
  |- running_tests.md
  |- code_conventions.md
  |- architecture_decisions.md
```

В CLAUDE.md ссылайтесь на эти файлы, например так:
```markdown
Подробные инструкции по сборке см. в `agent_docs/building_the_project.md`
```

**Важно**: используйте ссылки вида `file:line`, а не фрагменты кода, чтобы контекст не устаревал.

### 4. Ограничения качества

Когда создаёте или обновляете CLAUDE.md:

1. **Целевой объём**: держите файл короче 200 строк; чем короче, тем лучше
2. **Без правил стиля**: уберите инструкции по линтингу и форматированию
3. **Без инструкций под одну задачу**: унесите их в отдельные файлы
4. **Без фрагментов кода**: используйте ссылки на файлы
5. **Без повторов**: не дублируйте то, что уже есть в package.json или README

### 5. Обязательные разделы

Хорошо собранный CLAUDE.md включает:

```markdown
# Название проекта

Краткое описание в одну строку.

## Стек
- Основной язык и версия
- Ключевые фреймворки и библиотеки
- База данных или хранилище (если есть)

## Структура проекта
[Только для монорепозиториев или сложной структуры]
- `apps/` — точки входа приложений
- `packages/` — общие библиотеки

## Команды разработки
- Установка: `команда`
- Тесты: `команда`
- Сборка: `команда`

## Критичные соглашения
[Только неочевидные соглашения с большим влиянием]
- Соглашение 1 с кратким пояснением
- Соглашение 2 с кратким пояснением

## Известные проблемы / подводные камни
[То, обо что разработчики стабильно спотыкаются]
- Проблема 1
- Проблема 2
```

### 6. Антипаттерны, которых стоит избегать

**НЕ включайте:**
- Правила стиля кода (используйте линтеры)
- Документацию о том, как пользоваться Claude
- Длинные объяснения очевидных приёмов
- Скопированные примеры кода
- Общие лучшие практики («пишите чистый код»)
- Инструкции для конкретных задач
- Автоматически сгенерированное содержимое
- Длинные списки TODO

### 7. Чек-лист проверки

Перед завершением проверьте:

- [ ] Файл короче 200 строк; чем короче, тем лучше
- [ ] Каждая строка применима ко ВСЕМ сессиям
- [ ] Нет правил стиля и форматирования
- [ ] Нет фрагментов кода (используйте ссылки на файлы)
- [ ] Команды проверены и работают
- [ ] Для сложного проекта использовано постепенное раскрытие
- [ ] Критичные подводные камни записаны
- [ ] Нет повторов с README.md

## Формат результата

### Для `create` или по умолчанию:

1. Разберите проект
2. Набросайте CLAUDE.md по структуре выше
3. Покажите черновик на ревью
4. После одобрения запишите файл в нужное место

### Для `update`:

1. Прочитайте существующий CLAUDE.md
2. Сверьте его с лучшими практиками
3. Найдите:
   - Что убрать (правила стиля, фрагменты кода, инструкции под одну задачу)
   - Что сжать
   - Какой обязательной информации не хватает
4. Покажите изменения на ревью
5. Примените изменения после одобрения

### Для `audit`:

1. Прочитайте существующий CLAUDE.md
2. Составьте отчёт:
   - Текущее число строк против целевого
   - Доля содержимого, применимого ко всем сессиям
   - Список найденных антипаттернов
   - Рекомендации, что улучшить
3. Файл НЕ меняйте, только отчитайтесь

## Работа с AGENTS.md

Если пользователь просит создать или обновить AGENTS.md:

**С v2.1.277 Claude Code читает `AGENTS.md` напрямую как инструкции проекта** — но только если в рабочем каталоге и во всех каталогах выше нет `CLAUDE.md`, `.claude/CLAUDE.md` или `CLAUDE.local.md`. `~/.claude/CLAUDE.md`, управляемый CLAUDE.md и `.claude/rules/` в эту проверку не входят и продолжают загружаться рядом. Какие файлы читаются, задаёт настройка **Project instructions** в `/config`: `claude-md-or-agents-md` (по умолчанию), `claude-md-and-agents-md`, `claude-md` или `managed-only`. Где прямое чтение недоступно — версии до v2.1.277 (до v2.1.281 на Bedrock/Vertex/Foundry, в LLM-шлюзах или при отключённой телеметрии) либо первая сессия после обновления — подключайте файл из CLAUDE.md через `@AGENTS.md` или сделайте символическую ссылку `CLAUDE.md` на него.

AGENTS.md — файл контекста проекта для разных инструментов: тот же *вид* документа, что и CLAUDE.md, а не формат определения агента. Он нужен, чтобы несколько агентов для кода делили один набор соглашений проекта:
- Команды сборки, тестов и линтинга
- Стиль кода и архитектурные соглашения
- Раскладка репозитория и где что лежит

Субагенты задаются отдельно, в `.claude/agents/*.md`, а не в AGENTS.md.

Применяйте те же принципы:
- Держите текст собранным и коротким
- Используйте постепенное раскрытие
- Ссылайтесь на внешние документы, а не встраивайте их содержимое

## Заметки

- Прежде чем включать команду, проверьте, что она работает
- Если сомневаетесь, не включайте: меньше — значит лучше
- Системное напоминание говорит Claude, что CLAUDE.md «may or may not be relevant» («может относиться к делу, а может и нет») — чем больше шума, тем чаще его игнорируют
- Монорепозиториям больше всего помогает ясная структура ЧТО/ЗАЧЕМ/КАК
- CLAUDE.md для отдельного каталога должен быть ещё собраннее
