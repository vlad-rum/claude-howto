# Политика безопасности

## Обзор

Безопасность проекта Claude How To для нас важна. Этот документ описывает наши практики безопасности и то, как ответственно сообщать об уязвимостях.

## Поддерживаемые версии

Обновления безопасности мы даём для следующих версий:

| Версия | Статус | Поддержка до |
|---------|--------|---------------|
| Последняя (main) | ✅ Активна | Текущая + 6 месяцев |

**Примечание**: это образовательное руководство, поэтому мы поддерживаем актуальные практики и безопасность документации, а не классическую поддержку версий. Обновления попадают прямо в ветку main.

## Практики безопасности

### Безопасность кода

1. **Управление зависимостями**
   - Все зависимости Python закреплены в `requirements.txt`
   - Регулярные обновления через dependabot и ручное ревью
   - Сканирование безопасности Bandit при каждом коммите
   - Хуки pre-commit для проверок безопасности

2. **Качество кода**
   - Линтинг Ruff ловит типичные проблемы
   - Проверка типов mypy предотвращает уязвимости, связанные с типами
   - Хуки pre-commit обеспечивают стандарты
   - Все изменения проходят ревью до слияния

3. **Контроль доступа**
   - Защита ветки `main`
   - Обязательное ревью перед слиянием
   - Проверки статуса должны пройти до слияния
   - Ограниченная запись в репозиторий

### Безопасность документации

1. **Никаких секретов в примерах**
   - Все API-ключи в примерах — заглушки
   - Учётные данные никогда не прописываются в коде
   - Файлы `.env.example` показывают нужные переменные
   - Ясные предупреждения об управлении секретами

2. **Удачные практики безопасности**
   - Примеры показывают безопасные паттерны
   - Предупреждения о безопасности выделены в документации
   - Ссылки на официальные руководства по безопасности
   - Работа с учётными данными разобрана в соответствующих разделах

3. **Проверка содержания**
   - Вся документация проверяется на проблемы безопасности
   - Соображения безопасности есть в правилах участия
   - Внешние ссылки и источники проверяются

### Безопасность зависимостей

1. **Сканирование**
   - Bandit сканирует весь код Python на уязвимости
   - Проверки уязвимостей зависимостей через оповещения безопасности GitHub
   - Регулярные ручные аудиты безопасности

2. **Обновления**
   - Исправления безопасности применяются быстро
   - Крупные версии оцениваются внимательно
   - Список изменений включает обновления, связанные с безопасностью

3. **Прозрачность**
   - Обновления безопасности документируются в коммитах
   - Раскрытие уязвимостей ведётся ответственно
   - Публичные рекомендации по безопасности — когда это уместно

## Сообщение об уязвимости

### Проблемы безопасности, которые нам важны

Мы благодарны за сообщения о:
- **Уязвимостях в коде** скриптов или примеров
- **Уязвимостях зависимостей** в пакетах Python
- **Проблемах криптографии** в любых примерах кода
- **Изъянах аутентификации и авторизации** в документации
- **Рисках раскрытия данных** в примерах конфигурации
- **Уязвимостях инъекций** (SQL, команды и т. д.)
- **Проблемах SSRF/XXE/обхода пути**

### Проблемы безопасности вне области

Это вне области проекта:
- Уязвимости в самом Claude Code (сообщайте в Anthropic)
- Проблемы внешних сервисов или библиотек (сообщайте авторам)
- Социальная инженерия или обучение пользователей (к этому руководству не относится)
- Теоретические уязвимости без подтверждения на практике
- Уязвимости в зависимостях, о которых уже сообщено по официальным каналам

## Как сообщить

### Приватное сообщение (предпочтительно)

**Для чувствительных проблем безопасности используйте приватное сообщение об уязвимости на GitHub:**

1. Откройте: https://github.com/luongnv89/claude-howto/security/advisories
2. Нажмите «Report a vulnerability»
3. Заполните подробности уязвимости
4. Укажите:
   - Ясное описание уязвимости
   - Затронутый компонент (файл, раздел, пример)
   - Возможные последствия
   - Шаги воспроизведения (если применимо)
   - Предлагаемое исправление (если оно есть)

**Что дальше:**
- Мы подтвердим получение в течение 48 часов
- Мы разберёмся и оценим серьёзность
- Мы вместе с вами подготовим исправление
- Мы согласуем сроки раскрытия
- Мы укажем вас в рекомендации по безопасности (если вы не предпочитаете анонимность)

### Публичное сообщение

Для нечувствительных проблем или тех, что уже публичны:

1. **Откройте GitHub Issue** с меткой `security`
2. Укажите:
   - Заголовок: `[SECURITY]`, затем краткое описание
   - Подробное описание
   - Затронутый файл или раздел
   - Возможные последствия
   - Предлагаемое исправление

## Процесс реагирования на уязвимости

### Оценка (24 часа)

1. Мы подтверждаем получение сообщения
2. Мы оцениваем серьёзность по [CVSS v3.1](https://www.first.org/cvss/v3.1/specification-document)
3. Мы определяем, входит ли это в область
4. Мы связываемся с вами с первичной оценкой

### Разработка (1–7 дней)

1. Мы готовим исправление
2. Мы проверяем и тестируем исправление
3. Мы создаём рекомендацию по безопасности
4. Мы готовим заметки к релизу

### Раскрытие (зависит от серьёзности)

**Критическая (CVSS 9.0–10.0)**
- Исправление выпускается сразу
- Публикуется публичная рекомендация
- Сообщившим — уведомление за 24 часа

**Высокая (CVSS 7.0–8.9)**
- Исправление выпускается в течение 48–72 часов
- Сообщившим — уведомление за 5 дней
- Публичная рекомендация в момент релиза

**Средняя (CVSS 4.0–6.9)**
- Исправление выходит в ближайшем обычном обновлении
- Публичная рекомендация в момент релиза

**Низкая (CVSS 0.1–3.9)**
- Исправление входит в ближайшее обычное обновление
- Рекомендация в момент релиза

### Публикация

Мы публикуем рекомендации по безопасности, в которых есть:
- Описание уязвимости
- Затронутые компоненты
- Оценка серьёзности (балл CVSS)
- Версия с исправлением
- Обходные пути (если есть)
- Указание сообщившего (с его согласия)

## Удачные практики для тех, кто сообщает

### Перед сообщением

- **Проверьте проблему**: воспроизводится ли она стабильно?
- **Поищите существующие issue**: о ней уже сообщали?
- **Посмотрите документацию**: есть ли указания по безопасному использованию?
- **Проверьте исправление**: работает ли предложенное вами исправление?

### Когда сообщаете

- **Будьте конкретны**: укажите точные пути к файлам и номера строк
- **Дайте контекст**: почему это проблема безопасности?
- **Покажите последствия**: что сможет сделать злоумышленник?
- **Дайте шаги**: как нам это воспроизвести?
- **Предложите исправления**: как бы вы это исправили?

### После сообщения

- **Будьте терпеливы**: ресурсы у нас ограничены
- **Отвечайте**: быстро отвечайте на уточняющие вопросы
- **Держите конфиденциальность**: не раскрывайте публично до исправления
- **Уважайте координацию**: следуйте нашим срокам раскрытия

## Заголовки безопасности и конфигурация

### Безопасность репозитория

- **Защита ветки**: для изменений в ветке main нужны 2 одобрения
- **Проверки статуса**: все проверки CI/CD должны пройти
- **CODEOWNERS**: назначенные ревьюеры для ключевых файлов
- **Подписанные коммиты**: рекомендуются участникам

### Безопасность разработки

```bash
# Установить хуки pre-commit
pre-commit install

# Запустить проверки безопасности локально
bandit -c pyproject.toml -r scripts/
mypy scripts/ --ignore-missing-imports
ruff check scripts/
```

### Безопасность зависимостей

```bash
# Проверить известные уязвимости
pip install safety
safety check

# Или использовать pip-audit
pip install pip-audit
pip-audit
```

## Правила безопасности для участников

### Когда пишете примеры

1. **Никогда не храните секреты в коде**
   ```python
   # ❌ Плохо
   api_key = "sk-1234567890"

   # ✅ Хорошо
   api_key = os.getenv("API_KEY")
   ```

2. **Предупреждайте о последствиях для безопасности**
   ```markdown
   ⚠️ **Замечание о безопасности**: никогда не коммитьте файлы `.env` в git.
   Сразу добавьте их в `.gitignore`.
   ```

3. **Используйте безопасные значения по умолчанию**
   - Включайте аутентификацию по умолчанию
   - Используйте HTTPS, где это применимо
   - Проверяйте и очищайте входные данные
   - Используйте параметризованные запросы

4. **Документируйте соображения безопасности**
   - Объясняйте, почему безопасность важна
   - Показывайте безопасные и небезопасные паттерны
   - Ссылайтесь на авторитетные источники
   - Ставьте предупреждения на видное место

### Когда ревьюите материалы

1. **Ищите раскрытые секреты**
   - Сканируйте типичные паттерны (api_key=, password=)
   - Смотрите файлы конфигурации
   - Проверяйте переменные окружения

2. **Проверяйте безопасные практики кода**
   - Нет учётных данных в коде
   - Правильная проверка ввода
   - Безопасные аутентификация и авторизация
   - Безопасная работа с файлами

3. **Оценивайте последствия для безопасности**
   - Можно ли этим злоупотребить?
   - Какой худший случай?
   - Есть ли граничные случаи?
