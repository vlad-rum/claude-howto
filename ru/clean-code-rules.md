# Правила чистого кода для генерации кода ИИ

Эти правила направляют генерацию кода так, чтобы получался сопровождаемый код профессионального качества.

## Говорящие имена
- Берите имена, которые раскрывают намерение и объясняют, зачем сущность существует
- Избегайте дезинформации и бессмысленных различий (например, `data`, `info`, `manager`)
- Берите произносимые имена, по которым легко искать
- Имена классов: существительные (например, `UserAccount`, `PaymentProcessor`)
- Имена методов: глаголы (например, `calculateTotal`, `sendEmail`)
- Избегайте мысленных подстановок и кодировок (венгерская нотация, префиксы)

## Функции
- Держите функции маленькими (в идеале меньше 20 строк)
- Делайте только одно дело — принцип единственной ответственности
- Один уровень абстракции на функцию
- Ограничивайте число аргументов: в идеале 0–2, максимум 3, избегайте аргументов-флагов
- Без побочных эффектов — функция должна делать то, что обещает имя
- Отделяйте команды (меняют состояние) от запросов (возвращают сведения)
- Предпочитайте исключения кодам ошибок

## Комментарии
- Код должен объяснять себя сам — обходитесь без комментариев, когда это возможно
- Хорошие комментарии: юридические сведения, предупреждения, TODO, документация публичного API
- Плохие комментарии: избыточные, вводящие в заблуждение или объясняющие плохой код
- Никогда не комментируйте код — удаляйте его (система контроля версий хранит историю)
- Если нужен комментарий, подумайте, не лучше ли отрефакторить код

## Форматирование
- Держите файлы маленькими и сосредоточенными
- Вертикальное форматирование: связанные понятия рядом, пустые строки разделяют понятия
- Горизонтальное форматирование: ограничивайте длину строки (80–120 символов)
- Используйте единообразные отступы и стиль команды
- Группируйте связанные функции

## Объекты и структуры данных
- Объекты: прячьте данные за абстракциями, открывайте поведение через методы
- Структуры данных: открывают данные, поведения почти нет
- Закон Деметры: говорите только с непосредственными друзьями, избегайте `a.getB().getC().doSomething()`
- Не раскрывайте внутреннее устройство через геттеры и сеттеры без разбора

## Обработка ошибок
- Используйте исключения, а не коды возврата или флаги ошибок
- Пишите `try-catch-finally` первым, если код может упасть
- Давайте контекст в сообщениях исключений
- Не возвращайте `null` — возвращайте пустые коллекции или используйте Optional/Maybe
- Не передавайте `null` в аргументах

## Классы
- Маленькие классы: мера — обязанности, а не строки
- Принцип единственной ответственности: одна причина для изменения
- Высокая связность: переменные класса используются многими методами
- Слабая связанность: минимум зависимостей между классами
- Принцип открытости/закрытости: открыт для расширения, закрыт для изменения

## Модульные тесты
- Быстрые, независимые, повторяемые, самопроверяющиеся, своевременные (F.I.R.S.T.)
- Один assert на тест (или одно понятие)
- Качество тестового кода равно качеству продакшен-кода
- Читаемые имена тестов, которые описывают, что проверяется
- Шаблон Arrange-Act-Assert

## Принципы качества кода
- **DRY (Don't Repeat Yourself)**: без дублирования
- **YAGNI (You Aren't Gonna Need It)**: не стройте под гипотетическое будущее
- **KISS (Keep It Simple)**: избегайте лишней сложности
- **Правило бойскаута**: оставляйте код чище, чем нашли

## Запахи кода, которых следует избегать
- Длинные функции или классы
- Дублирующийся код
- Мёртвый код (неиспользуемые переменные, функции, параметры)
- Зависть к функциям (метод больше интересуется другим классом)
- Неуместная близость (классы знают друг о друге слишком много)
- Длинные списки параметров
- Одержимость примитивами (примитивы вместо маленьких объектов)
- Операторы switch/case (подумайте о полиморфизме)
- Временные поля (переменные класса, которые используются лишь иногда)

## Параллелизм
- Держите параллельный код отдельно от остального
- Ограничивайте область синхронизированных и заблокированных данных
- Используйте потокобезопасные коллекции
- Держите синхронизированные участки маленькими
- Знайте свои модели выполнения и примитивы

## Проектирование системы
- Отделяйте создание от использования (внедрение зависимостей)
- Используйте фабрики и строители для сложного создания объектов
- Программируйте на интерфейсы, а не на реализации
- Предпочитайте композицию наследованию
- Применяйте шаблоны проектирования, когда они упрощают, а не чтобы покрасоваться

## Рефакторинг
- Рефакторьте постоянно, а не большими порциями
- До и после всегда должны проходить тесты
- Маленькие шаги: одно изменение за раз
- Типичные рефакторинги: Extract Method, Rename, Move, Inline

## Документация
- Самодокументируемый код > комментарии > внешние документы
- Публичным API нужна ясная документация
- Включайте примеры в документацию
- Держите документацию рядом с кодом (в идеале в коде)

---

**Основной принцип**: код читают в 10 раз чаще, чем пишут. Оптимизируйте читаемость и сопровождаемость, а не остроумие.
