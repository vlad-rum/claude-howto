# Участие в Claude How To

Спасибо за интерес к этому проекту! Это руководство поможет понять, как участвовать эффективно.

## О проекте

Claude How To — наглядное руководство по Claude Code на примерах. Мы даём:
- **Диаграммы Mermaid**, которые объясняют, как устроены функции
- **Шаблоны, готовые к продакшену**, которые можно использовать сразу
- **Примеры из практики** с контекстом и удачными приёмами
- **Последовательные учебные пути** от начинающего до продвинутого

## Виды участия

### 1. Новые примеры или шаблоны
Добавляйте примеры для существующих функций (слэш-команды, навыки, хуки и т. д.):
- Код, который можно сразу скопировать
- Понятные объяснения, как это работает
- Сценарии использования и польза
- Советы по устранению неполадок

### 2. Улучшения документации
- Проясняйте запутанные разделы
- Исправляйте опечатки и грамматику
- Добавляйте недостающую информацию
- Улучшайте примеры кода

### 3. Руководства по функциям
Создавайте руководства по новым функциям Claude Code:
- Пошаговые туториалы
- Диаграммы архитектуры
- Типичные паттерны и антипаттерны
- Рабочие процессы из практики

### 4. Отчёты об ошибках
Сообщайте о проблемах, с которыми столкнулись:
- Опишите, чего вы ожидали
- Опишите, что произошло на самом деле
- Приложите шаги воспроизведения
- Укажите версию Claude Code и ОС

### 5. Обратная связь и предложения
Помогите улучшить руководство:
- Предлагайте более ясные объяснения
- Указывайте на пробелы в охвате
- Рекомендуйте новые разделы или другую структуру

## С чего начать

### 1. Форк и клонирование
```bash
git clone https://github.com/luongnv89/claude-howto.git
cd claude-howto
```

### 2. Создание ветки
Используйте говорящее имя ветки:
```bash
git checkout -b add/feature-name
git checkout -b fix/issue-description
git checkout -b docs/improvement-area
```

### 3. Настройка окружения

Хуки pre-commit запускают те же проверки, что и CI, локально перед каждым коммитом. Все пять проверок должны пройти, прежде чем PR примут.

**Обязательные зависимости:**

```bash
# Инструменты Python (uv — менеджер пакетов этого проекта)
pip install uv
uv venv
source .venv/bin/activate
uv pip install -r scripts/requirements-dev.txt

# Линтер Markdown (Node.js)
npm install -g markdownlint-cli

# Диаграммы Mermaid рисует Pele: нужен Node.js >= 20 (глобально ничего
# ставить не нужно). Проверьте версию:
node --version

# Установите pre-commit и включите хуки
uv pip install pre-commit
pre-commit install
```

**Проверьте настройку:**

```bash
pre-commit run --all-files
```

При первом запуске скачиваются Node.js 22 для хуков Mermaid (его ставит pre-commit, поэтому они работают даже без системного Node.js) и закреплённый пакет Pele в `scripts/.vendor-cache/pele/`; следующие запуски работают офлайн. Хуки Mermaid идут в строгом режиме и падают, если Pele не запускается. Чтобы сделать коммит офлайн до этой первой загрузки, пропустите их через `SKIP=mermaid,vietnamese-mermaid,japanese-mermaid`.

Хуки, которые запускаются при каждом коммите:

| Хук | Что проверяет |
|------|---------------|
| `markdown-lint` | Форматирование и структура Markdown |
| `cross-references` | Относительные ссылки, якоря, блоки кода |
| `mermaid-syntax` | Все блоки ` ```mermaid ` разбираются корректно |
| `link-check` | Внешние URL доступны |
| `build-epub` | EPUB собирается без ошибок (при изменениях `.md`) |

## Как добавлять примеры

### Добавление слэш-команды
1. Создайте файл `.md` в `01-slash-commands/`
2. Включите:
   - Ясное описание, что она делает
   - Сценарии использования
   - Инструкции по установке
   - Примеры использования
   - Советы по настройке
3. Обновите `01-slash-commands/README.md`

### Добавление навыка
1. Создайте каталог в `03-skills/`
2. Включите:
   - `SKILL.md` — основная документация
   - `scripts/` — вспомогательные скрипты, если нужны
   - `templates/` — шаблоны промптов
   - Пример использования в README
3. Обновите `03-skills/README.md`

### Добавление субагента
1. Создайте файл `.md` в `04-subagents/`
2. Включите:
   - Назначение агента и его возможности
   - Структуру системного промпта
   - Примеры сценариев
   - Примеры интеграции
3. Обновите `04-subagents/README.md`

### Добавление конфигурации MCP
1. Создайте файл `.json` в `05-mcp/`
2. Включите:
   - Пояснение конфигурации
   - Нужные переменные окружения
   - Инструкции по настройке
   - Примеры использования
3. Обновите `05-mcp/README.md`

### Добавление хука
1. Создайте файл `.sh` в `06-hooks/`
2. Включите:
   - Шебанг и описание
   - Понятные комментарии к логике
   - Обработку ошибок
   - Соображения безопасности
3. Обновите `06-hooks/README.md`

## Правила оформления

### Стиль Markdown
- Используйте ясные заголовки (H2 для разделов, H3 для подразделов)
- Держите абзацы короткими и сосредоточенными
- Используйте маркеры для списков
- Включайте блоки кода с указанием языка
- Добавляйте пустые строки между разделами

### Примеры кода
- Делайте примеры такими, чтобы их можно было сразу скопировать
- Комментируйте неочевидную логику
- Давайте и простой, и продвинутый вариант
- Показывайте сценарии из практики
- Отмечайте возможные проблемы

### Документация
- Объясняйте «зачем», а не только «что»
- Указывайте предварительные условия
- Добавляйте разделы по устранению неполадок
- Ссылайтесь на связанные темы
- Пишите так, чтобы было понятно начинающим

### JSON/YAML
- Используйте правильные отступы (единообразно 2 или 4 пробела)
- Добавляйте комментарии, поясняющие конфигурацию
- Включайте примеры проверки

### Диаграммы
- По возможности используйте Mermaid
- Делайте диаграммы простыми и читаемыми
- Добавляйте описание под диаграммой
- Ссылайтесь на соответствующие разделы

## Правила коммитов

Следуйте формату conventional commits:
```
type(scope): описание

[необязательное тело]
```

Типы:
- `feat`: новая функция или пример
- `fix`: исправление ошибки
- `docs`: изменения документации
- `refactor`: перестройка кода
- `style`: изменения форматирования
- `test`: добавление или изменение тестов
- `chore`: сборка, зависимости и т. п.

Примеры:
```
feat(slash-commands): Добавить генератор документации API
docs(memory): Улучшить пример личных предпочтений
fix(README): Исправить ссылку в оглавлении
docs(skills): Добавить полный навык код-ревью
```

## Перед отправкой

### Контрольный список
- [ ] Код следует стилю и соглашениям проекта
- [ ] У новых примеров есть ясная документация
- [ ] Файлы README обновлены (и локальный, и корневой)
- [ ] Нет секретной информации (API-ключи, учётные данные)
- [ ] Примеры проверены и работают
- [ ] Ссылки проверены и верны
- [ ] У файлов правильные права (скрипты исполняемые)
- [ ] Сообщение коммита ясное и содержательное

### Локальная проверка
```bash
# Запустить все проверки pre-commit (те же, что в CI)
pre-commit run --all-files

# Посмотреть свои изменения
git diff
```

## Процесс pull request

1. **Создайте PR с ясным описанием**:
   - Что это добавляет или исправляет?
   - Зачем это нужно?
   - Связанные issue (если есть)

2. **Приложите нужные подробности**:
   - Новая функция? Опишите сценарии
   - Документация? Объясните, что улучшилось
   - Примеры? Покажите до и после

3. **Свяжите issue**:
   - Используйте `Closes #123`, чтобы автоматически закрыть связанные issue

4. **Будьте терпеливы к ревью**:
   - Сопровождающие могут предложить улучшения
   - Дорабатывайте по обратной связи
   - Окончательное решение за сопровождающими

## Процесс код-ревью

Ревьюеры проверят:
- **Точность**: работает ли это так, как описано?
- **Качество**: готово ли это к продакшену?
- **Согласованность**: следует ли это паттернам проекта?
- **Документация**: ясная ли она и полная?
- **Безопасность**: нет ли уязвимостей?

## Политики проекта

### Секретная информация
- Никогда не коммитьте API-ключи, токены и учётные данные
- В примерах используйте заглушки
- Для файлов конфигурации прикладывайте `.env.example`
- Документируйте нужные переменные окружения

### Качество кода
- Держите примеры сосредоточенными и читаемыми
- Не усложняйте решения сверх меры
- Комментируйте неочевидную логику
- Тщательно проверяйте перед отправкой

### Интеллектуальная собственность
- Оригинальные материалы принадлежат автору
- Проект использует образовательную лицензию
- Уважайте существующие авторские права
- Указывайте авторство, где это нужно

## Безопасность

Добавляя примеры и документацию, следуйте безопасным практикам разработки:

- **Никогда не храните секреты и API-ключи в коде** — используйте переменные окружения
- **Предупреждайте о последствиях для безопасности** — отмечайте возможные риски
- **Используйте безопасные значения по умолчанию** — включайте защитные функции по умолчанию
- **Проверяйте входные данные** — показывайте правильную проверку и очистку ввода
- **Добавляйте заметки о безопасности** — документируйте соображения безопасности

Об уязвимостях читайте в [SECURITY.md](SECURITY.md): там описан процесс сообщения.
